# 함수형 프로그래밍은 왜 할당을 제한할까

> 함수형 프로그래밍은 동시성 문제를 더 잘 막는 기술이라기보다, 동시성 문제가 생길 수 있는 구조 자체를 줄이는 방식에 가깝다.

함수형 프로그래밍을 처음 생각하면 `map`, `filter`, `reduce` 같은 문법이 먼저 떠오른다.

하지만 Clean Architecture를 읽으며 더 중요하게 느낀 것은 문법이 아니었다.

핵심은 할당을 제한한다는 점이었다.

할당은 값을 바꾸는 일이다.

값을 바꿀 수 있다는 것은 상태가 변한다는 뜻이고, 상태가 변한다는 것은 시간에 따라 결과가 달라질 수 있다는 뜻이다.

특히 여러 흐름이 같은 상태를 동시에 바라보거나 수정한다면 문제가 더 커진다.

```text
Thread A → sharedState 읽기
Thread B → sharedState 읽기
Thread A → sharedState 수정
Thread B → sharedState 수정
```

이런 구조에서는 실행 순서에 따라 결과가 달라질 수 있다.

이것이 race condition의 출발점이다.

---

# 처음에는 Lock만 떠올렸다

동시성 문제를 처음 이해할 때는 lock을 먼저 떠올렸다.

공유 상태가 있고, 여러 스레드가 동시에 접근하니 lock으로 보호해야 한다고 생각했다.

```text
공유 상태가 있다
→ 동시에 접근하면 위험하다
→ lock으로 보호한다
```

이 방식은 자연스럽다.

하지만 lock은 공유 상태가 있다는 전제를 그대로 받아들인다.

문제의 원인을 없애기보다는, 위험한 접근을 통제한다.

그래서 lock을 쓰면 새로운 고민이 생긴다.

- 누가 lock을 잡는가
- 언제 lock을 놓는가
- lock 순서는 안전한가
- 다른 lock과 교착 상태가 생기지 않는가

lock은 공유 상태를 보호하지만, 동시에 복잡성도 만든다.

경합이 생기면 blocking, context switching, scheduler 개입 같은 비용도 발생할 수 있다.

즉 lock은 동시성 문제를 막기 위한 보호 장치지만, 그 자체로 또 다른 비용을 가진다.

---

# Atomic은 더 작은 단위의 안전성을 준다

그다음에는 atomic을 알게 됐다.

처음에는 `count++` 같은 코드를 단순한 한 줄로 생각하기 쉽다.

하지만 실제로는 읽고, 수정하고, 다시 쓰는 과정이다.

```text
read
modify
write
```

이 과정 중간에 다른 흐름이 끼어들면 lost update가 발생할 수 있다.

atomic은 이런 작은 단위의 연산을 원자적으로 만들어준다.

```text
공유 상태가 있다
→ 특정 연산을 원자적으로 수행한다
```

lock보다 더 작고 명확한 단위에서 안전성을 제공한다.

하지만 atomic도 여전히 공유 상태가 있다는 전제를 가진다.

공유 상태를 없애는 것이 아니라, 특정 연산이 깨지지 않도록 만드는 것이다.

그래서 내 이해는 이렇게 바뀌었다.

```text
Lock
→ 공유 상태에 접근하는 구간을 보호한다.

Atomic
→ 공유 상태에 대한 특정 연산을 안전하게 만든다.
```

둘 다 중요한 도구다.

하지만 둘 다 공유 변경 상태가 있다는 문제를 전제로 한다.

---

# 함수형 프로그래밍은 문제의 조건을 줄인다

함수형 프로그래밍은 조금 다르게 느껴졌다.

공유 변경 상태가 문제라면, 그 상태 자체를 줄인다.

상태를 직접 수정하지 않고, 이전 값으로부터 새로운 값을 만든다.

```text
oldState
→ newState
```

이렇게 보면 함수형 프로그래밍은 lock보다 더 강한 방향일 수 있다.

위험한 접근을 막는 것이 아니라, 위험한 접근이 필요한 상황 자체를 줄이기 때문이다.

```text
Lock
→ 문제가 생기지 않도록 보호한다.

Atomic
→ 문제가 생기는 연산을 안전하게 만든다.

Functional / Immutable
→ 문제가 생길 공유 변경 상태를 줄인다.
```

상태를 바꾸지 않으면, 같은 상태를 동시에 수정할 일이 줄어든다.

같은 상태를 동시에 수정할 일이 줄어들면, lock이 필요한 구간도 줄어든다.

lock이 줄어들면 deadlock이 생길 표면도 줄어든다.

그래서 함수형 프로그래밍은 race condition과 deadlock을 마법처럼 없애는 기술이 아니다.

그런 문제가 생길 수 있는 구조를 줄이는 방식에 가깝다.

---

# 성능 관점에서도 비용의 위치가 달라진다

공유 변경 상태를 줄이면 성능 측면에서도 좋아질 수 있다.

lock은 경합이 생기면 비용이 커진다.

```text
Thread A lock 획득
Thread B 대기
Thread A unlock
Thread B 재개
```

이 과정에서 context switching이나 scheduler 개입이 발생할 수 있다.

반대로 immutable state를 사용하면 같은 값을 동시에 수정하기 위해 기다릴 일이 줄어든다.

즉 lock 경합 비용을 줄일 수 있다.

하지만 함수형 방식이 항상 더 빠른 것은 아니다.

값을 직접 바꾸지 않고 새 값을 만들면 다른 비용이 생긴다.

- 객체 생성 비용
- 복사 비용
- 메모리 사용 증가
- GC 비용

성능이 무한하다면 모든 값을 새로 만들면 된다.

```text
state1
→ state2
→ state3
→ state4
```

하지만 현실에서는 성능이 유한하다.

그래서 함수형 프로그래밍은 비용이 사라지는 방식이 아니라, 비용의 위치를 바꾸는 방식으로도 볼 수 있다.

```text
Lock 기반
→ 경합, 대기, context switching 비용

Immutable 기반
→ 할당, 복사, GC 비용
```

중요한 것은 어떤 방식이 항상 빠른가가 아니다.

어떤 비용을 줄이고, 어떤 비용을 받아들일지 판단하는 것이다.

---

# 불변 상태는 변경 경로를 제한한다

함수형 프로그래밍을 Kotlin에서 생각하면 불변 `data class`와도 연결된다.

상태를 직접 수정하지 않고, 이전 상태에서 새로운 상태를 만든다.

```kotlin
data class RouteUiState(
    val isLoading: Boolean = false,
    val routes: List<Route> = emptyList()
)

_state.update { old ->
    old.copy(routes = old.routes + newRoute)
}
```

이 방식은 함수형 프로그래밍의 생각과 닿아 있다.

```text
oldState
→ newState
```

중요한 것은 외부에서 내부 데이터를 마음대로 고칠 수 없다는 점이다.

상태를 바꾸려면 상태를 소유한 곳에서 새 상태를 만들어 교체해야 한다.

```text
외부에서 내부 데이터 직접 수정
→ 불가능

상태 소유자 내부에서
→ oldState를 기반으로 newState 생성
→ 새 상태로 교체
```

이렇게 변경 경로가 제한된다.

상태를 아무나 바꿀 수 없고, 상태의 소유자만 새 상태를 만들 수 있다.

이것은 함수형 프로그래밍과 Ownership이 만나는 지점이라고 느꼈다.

---

# data class라고 항상 불변은 아니다

하지만 `data class`를 쓴다고 자동으로 불변이 되는 것은 아니다.

```kotlin
data class RouteUiState(
    val routes: MutableList<Route>
)
```

`val`은 참조를 바꾸지 못하게 할 뿐이다.

참조가 가리키는 객체의 내부 변경까지 막지는 못한다.

```kotlin
state.routes.add(newRoute)
```

이렇게 되면 상태 객체는 그대로인데 내부 값만 바뀐다.

변경 지점이 흐려지고, 누가 언제 상태를 바꿨는지 추적하기 어려워진다.

StateFlow 기반 UI에서도 예측 가능성이 떨어질 수 있다.

그래서 중요한 것은 `data class`를 쓰는 것이 아니다.

상태를 불변처럼 다루는 규약을 지키는 것이다.

```text
MutableList 노출
→ 모두가 수정할 수 있다.
→ 변경 책임이 흐려진다.

List 노출 + copy로 교체
→ 외부는 읽기만 한다.
→ 소유자만 새 상태를 만든다.
```

불변 상태는 단순히 값이 안 바뀐다는 뜻이 아니다.

상태 변경 권한을 제한한다는 뜻이다.

---

# 변경은 바깥으로 밀어내고, 계산은 안쪽에 둔다

Clean Architecture와 연결해보면 함수형 프로그래밍은 이런 방향으로 이해할 수 있다.

가능한 한 순수한 계산은 안쪽에 둔다.

그리고 부작용은 바깥쪽 경계로 밀어낸다.

```text
Business Rule
→ 가능한 순수한 계산

Boundary
→ UI
→ Database
→ Network
→ File
→ Device
```

비즈니스 로직 안에서는 입력이 같으면 같은 결과를 만들도록 한다.

외부 상태를 직접 바꾸는 일은 경계에서 처리한다.

변경 가능한 상태와 부작용은 사라지지 않는다.

다만 어디에 있는지 더 명확해진다.

좋은 구조는 모든 변경을 없애는 구조가 아니다.

변경이 일어나는 위치와 권한을 제한하는 구조다.

---

# 내가 얻은 결론

함수형 프로그래밍은 단순히 새로운 문법 스타일이 아니었다.

`map`, `filter`, `reduce`를 많이 쓰는 것이 핵심도 아니었다.

내가 이해한 핵심은 이것이다.

> 함수형 프로그래밍은 할당을 제한해 변경 가능한 상태를 줄이고, 그 결과 동시성 문제가 생길 수 있는 표면을 줄인다.

처음에는 동시성 문제를 lock으로 막는 방법을 배웠다.

그다음에는 atomic처럼 더 작은 단위에서 안전성을 보장하는 방법을 배웠다.

하지만 함수형 프로그래밍은 문제를 막는 방식이 아니라, 문제가 생길 조건 자체를 줄이는 방식에 가까웠다.

이제 좋은 동시성 구조를 볼 때 단순히 lock을 잘 쓰는지부터 보지 않게 됐다.

더 먼저 묻게 된다.

```text
이 상태는 꼭 공유되어야 하는가?
이 값은 꼭 변경되어야 하는가?
외부에서 이 데이터를 직접 바꿀 수 있는가?
변경은 상태의 소유자를 통해서만 일어나는가?
이 계산은 순수하게 만들 수 있는가?
```

결국 함수형 프로그래밍도 내가 계속 생각하던 질문으로 이어진다.

> 복잡성을 줄이기 위해 무엇을 제한할 것인가?
