# 컴포넌트는 변경과 배포의 경계다

> 컴포넌트는 클래스를 예쁘게 묶은 단위가 아니라, 따로 만들고 따로 배포할 수 있는 변경의 경계다.

Clean Architecture의 컴포넌트 파트를 읽으면서 조금 답답했다.

개념은 중요한 것 같은데 예시가 많지 않아서 한 번에 와닿지 않았다.

SOLID는 클래스와 인터페이스 예시를 떠올리면 그래도 이해가 됐다.

하지만 컴포넌트는 갑자기 배포, 릴리스, 재사용 단위 이야기가 나오면서 추상도가 올라간 느낌이었다.

그래서 먼저 컴포넌트가 왜 생겼는지부터 다시 생각해봤다.

---

# 처음에는 프로그램이 하나의 덩어리였다

초기의 프로그램은 하나의 큰 덩어리에 가까웠다.

```text
source code
→ compile
→ executable
```

작은 프로그램에서는 이 방식도 괜찮다.

하지만 코드가 커지면 문제가 생긴다.

```text
한 함수만 바꿨는데 전체를 다시 컴파일해야 한다.
여러 사람이 동시에 개발하기 어렵다.
이미 만든 코드를 다른 프로그램에서 재사용하기 어렵다.
프로그램이 커질수록 빌드 시간이 길어진다.
```

그래서 코드를 여러 파일로 나누기 시작했다.

```text
main.c
route.c
map.c
ui.c
```

각 파일은 따로 컴파일되고 object file이 된다.

```text
main.o
route.o
map.o
ui.o
```

그리고 마지막에 linker가 이들을 하나로 묶는다.

```text
main.o + route.o + map.o + ui.o
→ app
```

여기서 중요한 생각이 나온다.

> 컴파일은 따로 하고, 연결은 나중에 한다.

이 생각이 컴포넌트의 출발점에 가깝다고 느꼈다.

---

# 라이브러리는 재사용과 배포의 단위가 된다

object file이 많아지면 자주 쓰는 것들을 묶고 싶어진다.

```text
route.o
route_option.o
route_parser.o
```

이런 파일들을 묶으면 라이브러리가 된다.

```text
libroute.a
```

정적 라이브러리는 빌드나 링크 시점에 실행 파일 안으로 들어간다.

```text
app + libroute.a
→ executable
```

이후에는 동적 라이브러리도 등장한다.

```text
libroute.so
route.dll
```

동적 라이브러리는 실행 파일 안에 완전히 포함되는 것이 아니라, 실행 시점이나 로딩 시점에 연결될 수 있다.

```text
app
→ libroute.so 로드
```

이렇게 되면 라이브러리만 교체하거나, 여러 프로그램이 같은 라이브러리를 공유할 수 있다.

여기서 컴포넌트의 의미가 더 선명해진다.

> 컴포넌트는 독립적으로 배포 가능한 코드 묶음이다.

---

# JAR도 컴포넌트가 될 수 있다

JAR가 동적 라이브러리인지도 궁금했다.

정확히 말하면 JAR는 C/C++의 `.so`, `.dll` 같은 동적 라이브러리와 완전히 같지는 않다.

JAR는 Java class와 resource를 묶어둔 archive다.

```text
.class 파일
resource
META-INF
```

하지만 Java/Kotlin 세계에서 JAR는 라이브러리 배포 단위로 사용된다.

```text
route-domain.jar
route-engine.jar
map-sdk.jar
search-sdk.jar
```

사용자는 특정 버전의 JAR를 가져다 쓸 수 있다.

```kotlin
implementation("com.company:route-core:1.2.0")
```

이런 의미에서 JAR도 컴포넌트가 될 수 있다.

Android에서는 AAR가 비슷한 역할을 더 많이 한다.

```text
JAR
→ Java/Kotlin class와 resource 일부

AAR
→ Android resource, manifest, assets, native lib 등을 함께 포함
```

결국 중요한 것은 확장자가 아니다.

```text
독립적으로 빌드할 수 있는가?
독립적으로 배포할 수 있는가?
다른 코드가 그 단위에 의존할 수 있는가?
교체 가능한 경계가 되는가?
```

이 조건을 만족한다면 컴포넌트로 볼 수 있다.

그래서 내 기준으로 컴포넌트는 이렇게 정리된다.

> Boundary가 코드 안의 책임 경계라면, Component는 빌드와 배포 관점에서의 경계다.

---

# REP: 재사용하려면 릴리스 단위가 있어야 한다

REP는 Reuse/Release Equivalence Principle이다.

처음에는 이름이 어렵다.

하지만 예시로 보면 단순하다.

> 재사용 단위와 릴리스 단위는 같아야 한다.

누군가 내 코드를 가져다 쓴다고 해보자.

그런데 버전도 없고, 릴리스 기록도 없고, 변경 내역도 없다면 사용하는 입장에서는 불안하다.

```text
어제는 되던 함수가 오늘 바뀔 수 있다.
어떤 버전부터 필드가 추가됐는지 모른다.
버그 수정이 들어갔는지 모른다.
내가 쓰는 버전이 안전한지 판단하기 어렵다.
```

재사용되는 코드는 단순히 공통 코드가 아니다.

누군가가 믿고 가져다 쓰는 대상이다.

그러면 반드시 이런 것이 필요하다.

```text
버전
릴리스 노트
호환성 기준
변경 범위
업그레이드 판단 기준
```

예를 들어 `route-core.jar`를 재사용한다면 릴리스도 `route-core` 단위로 되어야 한다.

```text
route-core 1.2.0
route-core 1.2.1
route-core 1.3.0
```

그리고 사용하는 쪽은 이 정보를 보고 판단할 수 있어야 한다.

```text
이번 버전에서 뭐가 바뀌었는가?
내 코드에 영향이 있는가?
올려도 되는가?
버그 수정인가?
사양 변경인가?
호환성이 깨지는가?
```

회사 프로젝트의 공통 repo도 마찬가지다.

여러 플랫폼이 `exsl` 같은 공통 코드를 재사용한다면, `exsl`은 그냥 코드 저장소가 아니라 제품처럼 관리되어야 한다.

```text
exsl 1.2.0
→ 특정 플랫폼 영향 없음
→ RouteOption 버그 수정
→ CAN 송출 수정

exsl 1.3.0
→ AvoidOption 플랫폼 분리
→ 일부 API deprecated

exsl 2.0.0
→ RouteEngine interface 변경
→ 기존 플랫폼 수정 필요
```

릴리스가 없으면 재사용하는 쪽은 기준이 없다.

최신 코드를 당겨 쓰는 구조가 되고, 문제가 생겼을 때 어느 변경 때문인지 추적하기 어렵다.

내가 이해한 REP는 이렇게 정리된다.

> 재사용은 코드를 공유하는 것이 아니라, 변경 이력을 신뢰하는 것이다.

그리고 더 짧게 말하면 이렇다.

> 재사용하려면 배포 책임까지 가져야 한다.

---

# CCP: 같은 이유로 바뀌는 것들은 같이 묶어야 한다

CCP는 Common Closure Principle이다.

이 원칙은 SRP와 비슷하게 느껴졌다.

SRP가 클래스 단위에서 하나의 actor에 대해서만 책임지라고 말한다면, CCP는 컴포넌트 단위에서 같은 이유로 바뀌는 것들을 같이 묶으라고 말한다.

> 같은 이유로 바뀌는 것들은 같은 컴포넌트에 있어야 한다.

예를 들어 `AvoidOption` 사양이 바뀔 때 항상 함께 바뀌는 것들이 있다고 해보자.

```text
AvoidOptionParser
AvoidOptionMapper
AvoidOptionPolicy
AvoidOptionSender
```

이 클래스들이 여러 컴포넌트에 흩어져 있으면 하나의 사양 변경 때문에 여러 컴포넌트를 동시에 수정하고 릴리스해야 한다.

```text
avoid-policy.jar 수정
avoid-mapper.jar 수정
avoid-sender.jar 수정
```

이건 변경 이유가 여러 컴포넌트에 퍼진 것이다.

CCP 관점에서는 같은 변경 이유를 가진 것들을 한 컴포넌트 안에 묶는 편이 낫다.

```text
route-avoid-option-component
├─ AvoidOptionParser
├─ AvoidOptionMapper
├─ AvoidOptionPolicy
└─ AvoidOptionSender
```

그러면 `AvoidOption` 사양 변경은 이 컴포넌트 안에서 닫힌다.

```text
AvoidOption 사양 변경
→ route-avoid-option-component 수정/릴리스
```

내가 이해한 CCP는 이렇게 정리된다.

> CCP는 SRP를 컴포넌트 단위로 확장한 원칙이다.

그리고 더 정확히는 이렇다.

> 변경 이유를 기준으로 컴포넌트의 경계를 정하라는 원칙이다.

---

# CRP: 같이 쓰이지 않는 것들은 같이 묶지 않는다

CRP는 Common Reuse Principle이다.

이것도 이름은 어렵지만 예시로 보면 쉽다.

> 같이 재사용되지 않는 것들은 같은 컴포넌트에 묶지 마라.

예를 들어 이런 컴포넌트가 있다고 해보자.

```text
route-external.jar
├─ SomeIpSender
├─ NaviProviderSender
├─ CanSender
└─ DebugSender
```

내가 필요한 것은 `SomeIpSender` 하나뿐일 수 있다.

그런데 `route-external.jar`를 가져오면 `NaviProviderSender`, `CanSender`, `DebugSender`까지 함께 따라온다.

처음에는 안 쓰면 그만이라고 생각할 수 있다.

하지만 컴포넌트 단위에서는 그렇지 않다.

`CanSender`가 바뀌어서 `route-external.jar`가 새로 릴리스되면, `CanSender`를 사용하지 않는 쪽도 영향을 검토해야 한다.

```text
나는 SomeIpSender만 쓴다.
CanSender가 바뀐다.
route-external.jar가 새로 릴리스된다.
나도 dependency update를 검토한다.
나도 영향도 확인과 회귀 테스트 범위에 들어간다.
```

이것이 CRP가 막으려는 문제다.

사용하지 않는 것의 변경 때문에 나까지 흔들리는 것이다.

책바퀴 코드로 보면 이런 식으로 생각할 수 있다.

```text
현재 책바퀴
└─ app module
   ├─ core/ui/component/BookCover
   ├─ core/ui/component/PrimaryCta
   ├─ feature/neighborhood/data/mapper/KakaoRegionMapper
   ├─ feature/neighborhood/data/repository/NeighborhoodLocatorImpl
   └─ feature/book/data/remote/KakaoBookDto
```

지금은 하나의 `app` module 안에 있지만, 만약 나중에 이것들을 컴포넌트로 나눈다고 해보자.

이때 단순히 "공통으로 쓰일 수 있다"는 이유로 너무 큰 `core` 컴포넌트를 만들면 문제가 생길 수 있다.

예를 들어 어떤 화면은 `BookCover`나 `PrimaryCta` 같은 공통 UI 컴포넌트만 필요할 수 있다.

그런데 같은 컴포넌트 안에 `KakaoRegionMapper`나 `NeighborhoodLocatorImpl` 같은 동네 탐색 구현까지 함께 들어 있다면, UI만 쓰는 쪽도 위치 제공 방식이나 Kakao 응답 구조 변경의 영향 범위 안에 들어올 수 있다.

```text
나는 BookCover만 쓴다.
KakaoRegionMapper가 바뀐다.
큰 core component가 새로 릴리스된다.
나도 dependency update와 영향도 확인을 해야 한다.
```

이건 CRP 관점에서 좋지 않다.

같이 재사용되지 않는 것들이 같은 릴리스 단위에 묶였기 때문이다.

CRP 관점에서는 같이 재사용되는 단위로 나누는 것이 낫다.

```text
core-ui
├─ BookCover
├─ PrimaryCta
├─ ConfirmDialog
└─ ScreenStatus

neighborhood-data
├─ KakaoRegionMapper
├─ NeighborhoodLocatorImpl
└─ KakaoRegionCodeDto

book-data
├─ KakaoBookDto
├─ BookSearchRepositoryImpl
└─ BookRegistrationRepositoryImpl
```

이렇게 나누면 `core-ui`를 쓰는 쪽은 UI 컴포넌트 변경에만 주로 관심을 가지면 된다.

반대로 Kakao 지역 응답이나 위치 제공 방식 변경은 `neighborhood-data` 쪽 변경으로 제한할 수 있다.

내가 이해한 CRP는 이렇게 정리된다.

> CRP는 내가 쓰지 않는 것의 변경 때문에 나까지 흔들리지 않게 컴포넌트를 나누라는 원칙이다.

---

# REP, CCP, CRP는 서로 다른 질문을 한다

세 원칙은 비슷해 보이지만 묻는 질문이 다르다.

```text
REP
→ 재사용되는 단위와 릴리스되는 단위가 같은가?

CCP
→ 같은 이유로 바뀌는 것들이 같은 컴포넌트에 있는가?

CRP
→ 같이 쓰이지 않는 것들이 같은 컴포넌트에 묶여 있지는 않은가?
```

REP는 재사용과 릴리스의 관계를 본다.

CCP는 변경 이유를 본다.

CRP는 재사용되는 묶음을 본다.

---

# CCP와 CRP는 왜 균형이 필요할까

CCP와 CRP는 서로 긴장 관계가 있다.

CCP는 같이 바뀌는 것들을 묶으라고 한다.

CRP는 같이 쓰이지 않는 것들은 묶지 말라고 한다.

처음에는 이 말이 조금 이상하게 느껴졌다.

"같이 바뀌는 것들을 묶고, 같이 쓰이지 않는 것들을 나누면 되는 것 아닌가?"

둘 다 동시에 만족할 수 없는 것처럼 느껴졌다.

생각해보니 꼭 그런 것은 아니었다.

내가 이해한 가장 좋은 경우는 같이 바뀌는 단위와 같이 쓰이는 단위가 일치하는 경우였다.

```text
같이 바뀐다.
같이 쓰인다.
→ 같은 컴포넌트에 두기 좋다.
```

예를 들어 `AvoidOption` 관련 클래스들이 항상 같이 바뀌고, 사용하는 쪽도 항상 함께 가져간다면 같은 컴포넌트에 두는 것이 자연스럽다.

```text
route-avoid-option-component
├─ AvoidOptionParser
├─ AvoidOptionMapper
├─ AvoidOptionPolicy
└─ AvoidOptionSender
```

이 경우 CCP도 만족하고 CRP도 만족한다.

문제는 같이 바뀌는 단위와 같이 쓰이는 단위가 어긋날 때 생긴다.

```text
같이 바뀌지만 같이 쓰이지 않는다.
→ CCP는 묶고 싶어 한다.
→ CRP는 나누고 싶어 한다.

같이 쓰이지만 같이 바뀌지 않는다.
→ CRP는 묶어도 괜찮아 보인다.
→ CCP는 나누고 싶어 한다.
```

그래서 책에서 말한 균형이라는 말이 조금 이해됐다.

결국 무엇을 우선할지는 비용을 봐야 한다고 느꼈다.

배포와 검증 비용이 크다면 CCP를 더 우선하는 편이 현실적일 수 있다.

자동차나 플랫폼 프로젝트처럼 릴리스 승인, QE/QC 검증, 통합 테스트 비용이 큰 환경에서는 너무 잘게 나누는 것이 오히려 부담이 될 수 있다.

```text
avoid-policy.jar
avoid-mapper.jar
avoid-sender.jar
```

이렇게 나뉜 컴포넌트들이 항상 같이 바뀐다면, 매번 여러 컴포넌트를 함께 버전 올리고 검증해야 한다.

그럴 때는 같이 바뀌는 것들을 묶어서 릴리스 비용을 줄이는 편이 낫다.

반대로 불필요한 영향도 분석 비용이 더 크다면 CRP를 더 강하게 봐야 한다.

예를 들어 어떤 플랫폼은 `SomeIpSender`만 쓰는데, 같은 컴포넌트 안의 `CanSender` 변경 때문에 매번 영향도 분석과 회귀 테스트를 해야 한다면 그 비용도 크다.

```text
나는 SomeIpSender만 쓴다.
CanSender가 바뀐다.
route-external.jar가 새로 릴리스된다.
나도 영향도 분석을 해야 한다.
```

이런 일이 반복된다면 컴포넌트를 나누는 쪽이 더 나을 수 있다.

내 기준으로는 이렇게 정리된다.

```text
릴리스 비용이 더 크다
→ CCP를 더 우선한다.
→ 같이 바뀌는 것들을 묶어 릴리스 횟수를 줄인다.

불필요한 영향도 분석 비용이 더 크다
→ CRP를 더 우선한다.
→ 같이 쓰이지 않는 것들을 나눠 영향 범위를 줄인다.
```

우리 같은 환경에서는 처음에는 CCP를 더 우선하는 것이 현실적일 수 있다고 느꼈다.

컴포넌트가 너무 많으면 버전 관리와 배포가 어려워지기 때문이다.

하지만 공통 컴포넌트가 커지고, 사용자마다 사용하는 범위가 달라지고, 무관한 변경 때문에 여러 플랫폼이 계속 흔들리기 시작하면 CRP를 더 강하게 봐야 한다는 생각이 들었다.

결국 컴포넌트 경계는 처음부터 완벽하게 정해지는 것이 아니다.

무엇이 더 큰 비용이 되었는지에 따라 이동한다.

---

# 나누면 빌드는 편해지지만 통합 검증은 어려워진다

컴포넌트를 나누면 빌드 에러가 줄어들지 않을까 하는 생각도 들었다.

정확히는 빌드 에러가 사라지는 것이 아니라, 빌드 에러가 전파되는 범위가 줄어든다.

예를 들어 하나의 큰 공통 모듈 안에 route, map, search, external이 모두 들어 있다면 작은 변경 하나가 전체 빌드를 깨뜨릴 수 있다.

```text
Route 변경
→ 공통 모듈 빌드 실패
→ 모든 플랫폼 영향
```

하지만 컴포넌트를 나누면 실패 범위를 좁힐 수 있다.

```text
exsl-route 빌드 실패
→ route 관련 사용자 영향

exsl-map 빌드 성공
exsl-search 빌드 성공
```

이 점에서 컴포넌트 분리는 빌드 안정성을 높이는 데 도움이 될 수 있다.

빌드 에러도 결국 변경 전파의 한 형태이기 때문이다.

하지만 그 대신 다른 비용도 생긴다.

컴포넌트를 나누면 각 컴포넌트 내부 테스트는 쉬워질 수 있지만, 컴포넌트 사이의 통합 테스트는 어려워질 수 있다.

예를 들어 하나의 기능이 RP와 MD를 함께 거친다고 해보자.

```text
RP
→ 경로 상태 계산
→ 계약으로 상태 제공

MD
→ 상태 수신
→ 지도 표현
→ 화면 전환
```

각 컴포넌트는 따로 보면 정상일 수 있다.

하지만 붙였을 때 문제가 생길 수 있다.

```text
계약 해석이 다르다.
상태 업데이트 타이밍이 다르다.
버전 조합이 맞지 않는다.
이벤트 순서가 어긋난다.
필드의 의미를 다르게 이해한다.
```

그래서 컴포넌트를 나눈다면 테스트도 같이 나뉘어야 한다고 느꼈다.

```text
컴포넌트 내부 테스트
→ 각 컴포넌트가 자기 책임을 잘 수행하는가?

계약 테스트
→ 컴포넌트 사이의 interface나 protocol 의미가 서로 맞는가?

통합 테스트
→ 실제 조합에서 end-to-end로 동작하는가?
```

컴포넌트 분리는 통합 테스트를 없애는 것이 아니다.

오히려 통합 테스트를 계약 테스트와 end-to-end 테스트로 나누어 관리해야 할 수 있다.

그래서 컴포넌트를 나누는 판단에는 테스트 비용도 포함되어야 한다.

```text
나누면 줄어드는 비용
→ 빌드 실패 전파
→ 변경 영향 범위
→ 불필요한 회귀 테스트

나누면 생기는 비용
→ 계약 관리
→ 버전 호환성
→ 통합 테스트
→ 조합 검증
```

결국 컴포넌트 분리는 빌드 에러 전파를 줄이는 대신, 계약과 통합 검증 비용을 만들 수 있다.

이 비용을 감당할 테스트 구조가 없다면 무작정 나누는 것도 답은 아니라고 느꼈다.

---

# SRP와 ISP도 같은 방식으로 충돌할까

여기서 SRP와 ISP도 떠올랐다.

CCP가 SRP의 컴포넌트 버전처럼 보인다면, CRP는 ISP의 컴포넌트 버전처럼 보인다.

```text
SRP
→ 같은 actor에 의해 바뀌는 책임만 하나의 클래스에 둔다.

CCP
→ 같은 이유로 바뀌는 클래스들을 하나의 컴포넌트에 둔다.

ISP
→ 사용하지 않는 함수에 의존하지 않게 한다.

CRP
→ 사용하지 않는 클래스가 포함된 컴포넌트에 의존하지 않게 한다.
```

그렇다면 SRP와 ISP도 충돌할 수 있을까?

처음에는 비슷하게 충돌할 것 같았다.

SRP는 같은 actor의 변경 이유를 한곳에 모으라고 말한다.

ISP는 사용하는 쪽이 필요 없는 계약까지 알지 않게 하라고 말한다.

그래서 SRP만 강하게 보면 이런 생각을 할 수 있다.

```text
같은 actor가 관리하니까 하나의 클래스나 인터페이스에 모아도 되지 않을까?
```

반대로 ISP만 강하게 보면 이런 생각을 할 수 있다.

```text
사용자마다 필요한 함수가 다르니 전부 잘게 나누어야 하지 않을까?
```

생각해보니 SRP와 ISP는 CCP와 CRP처럼 같은 경계를 두고 정면으로 충돌하는 관계는 아닌 것 같았다.

CCP와 CRP는 둘 다 컴포넌트 경계를 직접 다룬다.

그래서 하나는 묶으라고 하고, 하나는 나누라고 한다.

```text
CCP
→ 같이 바뀌면 같은 컴포넌트에 묶어라.

CRP
→ 같이 쓰이지 않으면 같은 컴포넌트에 묶지 마라.
```

반면 SRP와 ISP는 보는 대상이 조금 다르다.

SRP는 구현 책임의 변경 이유를 본다.

ISP는 사용자에게 노출되는 계약의 크기를 본다.

예를 들어 하나의 actor가 관리하는 외부 연동 정책이 있다고 해보자.

구현 관점에서는 같은 actor가 관리하므로 한곳에 둘 수 있다.

하지만 사용하는 쪽이 SOME/IP만 필요한데 CAN 송출 함수까지 알아야 한다면 인터페이스는 너무 크다.

이 경우 구현은 같은 책임 아래에 둘 수 있지만, 노출되는 계약은 분리해야 한다.

```text
구현 책임
→ 같은 actor가 관리하므로 함께 둘 수 있다.

사용자 계약
→ 사용하는 쪽이 필요한 만큼만 보게 나눈다.
```

즉 SRP는 "누가 변경을 요구하는가"를 묻고, ISP는 "누가 무엇을 사용해야 하는가"를 묻는다.

그래서 SRP와 ISP는 구현 책임과 노출 계약을 분리하면 동시에 만족시킬 수 있다고 이해했다.

```text
RouteExternal
→ 하나의 actor가 관리하는 구현체일 수 있다.
→ SRP 관점에서 하나의 책임일 수 있다.

SomeIpRouteSender
CanRouteSender
NaviProviderRouteSender
→ 사용하는 쪽이 필요한 만큼만 보는 계약이다.
→ ISP 관점에서 나뉜 interface다.
```

즉 구현체는 하나일 수 있지만, 사용자가 바라보는 interface는 여러 개일 수 있다.

이 점에서 SRP와 ISP는 정면 충돌이라기보다 서로 보완될 수 있다고 느꼈다.

다만 이것을 구분하지 못하면 문제가 생긴다.

SRP를 이유로 너무 큰 interface를 만들면 ISP를 어길 수 있다.

ISP를 이유로 무작정 구현체까지 잘게 쪼개면 오히려 같은 actor의 변경 이유가 흩어질 수 있다.

그래서 나눌 때는 변경 이유만 봐도 부족하고, 사용하는 쪽의 관점만 봐도 부족하다고 느꼈다.

결국 경계는 정답을 외워서 정할 수 있는 문제가 아니었다.

변경 이유, 사용하는 쪽의 관점, 릴리스 비용을 함께 봐야 했다.

---

# 내가 얻은 결론

컴포넌트는 단순한 폴더나 클래스 묶음이 아니었다.

컴포넌트는 독립적으로 빌드하고 배포할 수 있는 변경의 경계였다.

그래서 컴포넌트를 나눌 때는 코드가 비슷한지만 보면 안 된다.

```text
누가 재사용하는가?
어떤 단위로 릴리스되는가?
같은 이유로 바뀌는가?
같이 쓰이는가?
변경이 생겼을 때 누가 영향받는가?
```

이 질문을 봐야 한다.

REP는 재사용하려면 릴리스 책임이 필요하다는 것을 알려준다.

CCP는 같은 이유로 바뀌는 것들을 같은 컴포넌트에 묶으라고 말한다.

CRP는 같이 쓰이지 않는 것들을 같은 컴포넌트에 묶지 말라고 말한다.

그리고 CCP와 CRP는 항상 동시에 만족되는 것은 아니다.

같이 바뀌는 단위와 같이 쓰이는 단위가 일치하면 가장 좋다.

하지만 둘이 어긋나면 릴리스 비용과 불필요한 영향도 분석 비용 중 무엇이 더 큰지 봐야 한다.

여기에 테스트 비용도 같이 봐야 한다.

컴포넌트를 나누면 빌드 실패 전파는 줄어들 수 있지만, 컴포넌트 사이의 계약과 통합 검증 비용은 늘어날 수 있기 때문이다.

내 기준으로 컴포넌트 원칙은 이렇게 정리된다.

> 컴포넌트는 변경과 배포를 어디서 끊을지 정하는 단위다.

그리고 더 현실적으로 말하면 이렇다.

> 같이 바뀌고 같이 쓰이는 것을 같은 릴리스 단위에 두는 것이 가장 이상적이다.

만약 그렇게 되지 않는다면, 컴포넌트 경계는 비용이 더 크게 발생하는 쪽을 줄이는 방향으로 다시 조정해야 한다고 느꼈다.
