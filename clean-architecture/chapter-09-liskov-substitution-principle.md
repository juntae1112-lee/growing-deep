# 같은 타입처럼 쓰려면 같은 약속을 지켜야 한다

> 리스코프 치환 원칙은 상속을 잘 쓰는 법이라기보다, 같은 타입이라고 부를 수 있는 기준을 알려주는 원칙이다.

리스코프 치환 원칙을 처음 보면 조금 멀게 느껴진다.

상속받은 클래스는 부모 클래스로 치환 가능해야 한다.

문장 자체는 이해된다.

하지만 실무에서 바로 떠오르는 사례는 생각보다 많지 않았다.

왜냐하면 나는 평소에 상속과 override를 그렇게 많이 쓰지 않는다.

그리고 사용자 쪽에서 다르게 써야 하는 순간이 보이면, 보통은 같은 타입으로 묶지 않고 분리하려고 했다.

그래서 처음에는 이런 생각이 들었다.

"이 원칙은 내 실무와 조금 거리가 있는 것 아닌가?"

그런데 다시 생각해보니 오히려 반대였다.

내가 막연하게 불편해하던 지점이 리스코프 치환 원칙과 닿아 있었다.

리스코프 치환 원칙은 나에게 새로운 패턴을 알려준 원칙이라기보다, 내가 이미 피하려고 했던 구조가 왜 위험한지 설명해주는 원칙에 가까웠다.

---

# 상속은 구현이 아니라 계약을 물려받는 것이다

처음에는 상속을 코드 재사용의 방법으로 생각하기 쉽다.

부모에 공통 로직을 두고, 자식이 필요한 부분만 바꾼다.

하지만 리스코프 치환 원칙 관점에서 보면 상속은 단순히 구현을 물려받는 것이 아니다.

부모가 가진 계약도 함께 물려받는 것이다.

예를 들어 이런 부모 타입이 있다고 해보자.

```kotlin
interface RouteEngine {
    fun requestRoute(request: RouteRequest): RouteResult
}
```

이 함수의 모양만 보면 단순하다.

요청을 넣으면 결과가 나온다.

하지만 실제로 중요한 것은 함수 모양이 아니라 이 함수가 가진 약속이다.

```text
requestRoute를 호출하면 경로 탐색을 요청한다.
성공하면 경로 결과를 반환한다.
실패하면 실패 결과를 반환한다.
호출자는 엔진 종류를 몰라도 같은 방식으로 사용할 수 있다.
```

이 약속이 부모 타입의 계약이다.

자식 구현체는 내부에서 서버를 호출해도 되고, 로컬 엔진을 사용해도 되고, 캐시를 사용해도 된다.

내부 구현은 달라도 된다.

하지만 호출자가 믿는 약속은 깨면 안 된다.

---

# override는 같은 약속을 보장하지 않는다

override는 문법적으로 같은 함수임을 보장한다.

하지만 의미적으로 같은 약속임을 보장하지는 않는다.

예를 들어 모두 같은 함수를 override할 수 있다.

```kotlin
override fun requestRoute(request: RouteRequest): RouteResult
```

하지만 실제 동작이 이렇게 다르다면 어떨까.

```text
A 엔진은 requestRoute만 호출하면 된다.
B 엔진은 requestRoute 전에 prepare를 먼저 호출해야 한다.
C 엔진은 특정 옵션을 조용히 무시한다.
D 엔진은 실패해도 실패 결과를 반환하지 않는다.
```

시그니처는 같다.

컴파일도 된다.

하지만 호출자는 더 이상 `RouteEngine`이라는 부모 타입만 믿고 사용할 수 없다.

호출자는 구현체가 무엇인지 알아야 한다.

```kotlin
if (engine is PrepareRequiredEngine) {
    engine.prepare()
}

val result = engine.requestRoute(request)
```

이 순간 같은 타입이라는 말은 약해진다.

부모 타입으로 받았지만 자식 타입을 알아야 하기 때문이다.

내가 이해한 리스코프 치환 원칙의 핵심은 여기에 있다.

> 구현체마다 내부 동작이 다른 것은 괜찮다.  
> 하지만 호출자가 구현체마다 다르게 사용해야 한다면, 같은 타입으로 치환 가능한 구조가 아니다.

---

# 다르게 써야 한다면 같은 타입이 아니다

처음에는 "다르게 사용한다"는 말을 매개변수나 리턴 타입이 다른 경우로만 생각했다.

하지만 실제로 더 위험한 차이는 함수 모양이 아니라 의미에서 생긴다.

```text
호출 전 조건이 다르다.
호출 후 보장이 다르다.
실패 처리 방식이 다르다.
상태 변화가 다르다.
옵션의 의미가 다르다.
```

이런 차이는 컴파일러가 잡아주지 않는다.

함수 이름도 같고, 매개변수도 같고, 리턴 타입도 같을 수 있다.

하지만 호출자는 구현체마다 다른 주의사항을 알아야 한다.

이것이 더 위험하다.

겉으로는 같은 타입인데 실제로는 다른 계약을 가지고 있기 때문이다.

그래서 판단 기준은 단순해진다.

```text
부모 타입으로 받았을 때,
자식 타입을 몰라도 같은 방식으로 사용할 수 있는가?
```

그렇다면 같은 타입으로 묶을 수 있다.

하지만 자식 타입을 알아야 안전하게 사용할 수 있다면, 그건 같은 타입이 아닐 가능성이 높다.

이 기준으로 보면 내가 실무에서 LSP 위반 사례를 많이 떠올리지 못한 이유도 조금 이해된다.

나는 이런 냄새가 나면 보통 상속 구조로 밀어붙이지 않았다.

사용하는 쪽이 다르게 알아야 하는 순간, 이미 같은 계약이 아니라고 느꼈기 때문이다.

그동안은 이것을 단순히 "분리하는 게 맞다" 정도로 생각했다.

하지만 리스코프 치환 원칙으로 보면 그것은 거짓 추상화를 피하는 일이었다.

---

# 부모 계약을 넓히면 해결될까

여기서 한 가지 더 헷갈리는 지점이 있었다.

만약 어떤 엔진만 `prepare`가 필요하다면, 부모에 `prepare`를 추가하면 되는 것 아닐까?

예를 들면 이런 식이다.

```kotlin
interface RouteEngine {
    fun prepare()
    fun requestRoute(request: RouteRequest): RouteResult
}
```

그러면 호출자는 모든 엔진을 같은 방식으로 사용할 수 있다.

```kotlin
engine.prepare()
val result = engine.requestRoute(request)
```

어떤 자식은 `prepare`가 필요 없을 수도 있다.

그 경우 빈 구현을 둘 수 있다.

```kotlin
class LocalRouteEngine : RouteEngine {
    override fun prepare() {
        // do nothing
    }

    override fun requestRoute(request: RouteRequest): RouteResult {
        // local route search
    }
}
```

이렇게 하면 LSP만 보면 괜찮아 보인다.

호출자는 자식 타입을 몰라도 같은 순서로 호출할 수 있기 때문이다.

하지만 이것이 항상 좋은 설계라는 뜻은 아니다.

`prepare`가 모든 엔진의 자연스러운 생명주기라면 괜찮다.

예를 들어 모든 엔진이 초기화, 탐색, 해제라는 공통 흐름을 가진다면 부모 계약에 포함될 수 있다.

```text
initialize
requestRoute
release
```

하지만 `prepare`가 특정 엔진 하나의 내부 사정 때문에 부모로 올라온 것이라면 이야기가 달라진다.

그 순간 모든 자식이 필요 없는 함수를 알게 된다.

어떤 자식은 아무것도 하지 않는 함수를 구현해야 한다.

호출자도 실제로는 일부 엔진에만 필요한 개념을 공통 계약처럼 사용하게 된다.

이건 LSP를 피하려다 인터페이스 분리 원칙을 어기는 방향으로 갈 수 있다.

```text
기존 문제
→ 호출자가 특정 자식만 다르게 다룬다.
→ LSP 위반

잘못된 해결
→ 부모에 특정 자식에게만 필요한 함수를 올린다.
→ 안 쓰는 자식도 빈 구현을 가진다.
→ ISP 위반
```

즉 부모 계약을 넓히는 것은 언제나 신중해야 한다.

LSP를 지키기 위해 부모 계약을 넓힐 수는 있다.

하지만 그 계약이 모든 자식에게 자연스러운지 확인해야 한다.

그렇지 않으면 치환 가능성은 얻었지만 인터페이스는 오염된다.

더 나은 해결은 특정 구현체의 내부 준비 과정을 호출자에게 드러내지 않는 것이다.

```kotlin
class CenterRouteEngine : RouteEngine {
    override fun requestRoute(request: RouteRequest): RouteResult {
        prepareIfNeeded()
        return requestCenterRoute(request)
    }
}
```

호출자는 여전히 하나만 알면 된다.

```kotlin
val result = engine.requestRoute(request)
```

이 구조에서는 `prepare`가 호출자의 책임으로 올라오지 않는다.

특정 구현체의 내부 사정은 구현체 안에 머문다.

그래서 중요한 질문은 이것이다.

```text
이 함수는 모든 구현체가 자연스럽게 가져야 하는 계약인가?
아니면 특정 구현체의 사정을 부모로 끌어올린 것인가?
```

후자라면 부모에 올리면 안 된다.

그건 추상화를 정리한 것이 아니라, 특정 구현체의 사정을 전체 타입에 퍼뜨린 것이다.

# 삭제해도 되는 구현과 삭제하면 안 되는 계약

실무에서 떠올랐던 애매한 예도 있다.

어떤 부모 parser의 `parse` 함수가 있었다.

부모 구현은 데이터를 parse하면서 priority도 함께 parse하고 저장했다.

그런데 자식 parser에서는 priority가 필요 없었다.

그래서 자식 구현에서는 priority parse와 save를 제거했다.

이것은 리스코프 치환 원칙을 어긴 것일까?

처음에는 헷갈렸다.

부모가 하던 일을 자식이 하지 않았기 때문이다.

하지만 기준은 부모가 내부에서 무엇을 했느냐가 아니다.

부모의 외부 계약이 무엇이었느냐가 중요하다.

만약 부모의 계약이 이것이라면 괜찮을 수 있다.

```text
parse를 호출하면 필요한 데이터를 파싱하고,
해당 parser가 사용할 수 있는 상태를 만든다.
```

이 경우 priority는 부모 구현의 일부였을 뿐이다.

자식에게 priority가 필요 없다면 저장하지 않아도 된다.

호출자가 동일하게 `parse`를 호출하고, 이후 동일한 의미의 결과를 얻는다면 치환 가능성은 깨지지 않는다.

하지만 부모의 계약이 이것이라면 다르다.

```text
parse를 호출하면 priority가 반드시 저장된다.
parse 이후 priority 기반 동작을 사용할 수 있다.
```

이 경우 priority 저장은 내부 구현이 아니라 외부 계약이다.

자식이 이 동작을 제거하면 호출자가 믿던 약속이 깨진다.

결국 중요한 질문은 이것이다.

```text
priority 저장은 부모의 내부 구현인가?
아니면 호출자가 믿는 외부 계약인가?
```

내부 구현이라면 자식이 달라도 된다.

외부 계약이라면 자식도 지켜야 한다.

자식이 부모의 모든 구현을 똑같이 따라야 하는 것은 아니다.

하지만 부모가 밖으로 약속한 것은 지켜야 한다.

---

# 다른 계약이라면 함수를 분리해야 한다

부모의 계약을 지킬 수 없다면 억지로 같은 함수를 override하면 안 된다.

그럴 때는 계약을 다시 잡거나, 함수를 분리해야 한다.

예를 들어 모든 엔진이 같은 방식으로 사용할 수 있다면 부모 계약을 더 명확히 만들 수 있다.

```kotlin
interface RouteEngine {
    fun requestRoute(request: RouteRequest): RouteResult
}
```

각 엔진별 사전 처리나 내부 차이는 구현체 안으로 숨긴다.

호출자는 여전히 같은 방식으로 사용한다.

```kotlin
val result = engine.requestRoute(request)
```

하지만 호출 순서, 준비 과정, 실패 처리, 결과 의미가 완전히 다르다면 같은 함수로 숨기면 안 된다.

그때는 분리하는 편이 낫다.

```kotlin
interface CenterRouteSearch {
    fun requestCenterRoute(request: CenterRouteRequest): CenterRouteResult
}

interface LocalRouteSearch {
    fun requestLocalRoute(request: LocalRouteRequest): LocalRouteResult
}
```

이것은 재사용을 포기하는 것이 아니다.

다른 계약을 같은 함수처럼 보이게 만들지 않는 것이다.

거짓 추상화를 제거하는 것이다.

좋은 추상화는 차이를 없애는 것이 아니다.

호출자가 몰라도 되는 차이를 내부로 숨기고, 호출자가 반드시 알아야 하는 차이는 밖으로 드러낸다.

리스코프 치환 원칙은 그 경계를 확인하게 만든다.

---

# 내가 얻은 결론

나에게 리스코프 치환 원칙은 상속을 많이 쓰라는 말이 아니었다.

오히려 상속을 쉽게 믿지 말라는 말에 가까웠다.

같은 부모를 상속받았다는 이유만으로 같은 타입이라고 말할 수는 없다.

같은 함수를 override했다는 이유만으로 같은 약속을 지킨다고 말할 수도 없다.

중요한 것은 호출자가 부모 타입만 보고 안전하게 사용할 수 있는가다.

그래서 실무에서 LSP를 볼 때 꼭 거창한 상속 계층을 찾을 필요는 없다고 느꼈다.

오히려 질문은 더 단순하다.

```text
같은 타입으로 묶인 것들을
정말 같은 방식으로 믿고 사용할 수 있는가?
```

이 질문에 답하지 못하면, 그 타입은 아직 충분히 정직하지 않다.

그래서 내 기준은 이렇게 정리된다.

> 부모를 상속받았으면 부모의 계약도 물려받아야 한다.  
> 그 계약을 지킬 수 없다면, 같은 함수를 억지로 override하지 말고 분리해야 한다.

그리고 더 짧게 말하면 이것이다.

> 다르게 써야 한다면 같은 타입이 아니다.

리스코프 치환 원칙은 상속 구조를 예쁘게 만드는 원칙이 아니었다.

같은 타입이라고 부를 수 있는 최소한의 정직함을 지키는 원칙이었다.

그리고 LSP를 지키기 위해 부모 계약을 넓히는 순간에는 한 번 더 물어봐야 한다.

> 이 계약은 모든 자식에게 자연스러운가?

그렇지 않다면 LSP는 지킨 것처럼 보여도, 다른 원칙을 망가뜨리고 있을 수 있다.
