# SOLID를 내 경험으로 다시 이해하기

> SOLID는 객체지향 원칙을 외우기 위한 목록이 아니라, 변경 이유가 잘못된 곳으로 전파되지 않게 막는 기준에 가까웠다.

SOLID를 하나씩 읽다 보니 처음에는 각각 다른 이야기를 하는 것처럼 보였다.

SRP는 책임을 말하고, OCP는 확장을 말하고, LSP는 치환 가능성을 말하고, ISP는 인터페이스 분리를 말하고, DIP는 의존성 방향을 말한다.

하지만 실무 경험과 연결해보니 결국 비슷한 질문으로 모였다.

```text
이 변경은 어디에서 막혀야 하는가?
이 책임은 누가 가져야 하는가?
이 계약은 누가 믿고 사용할 수 있는가?
이 구현의 변화가 어디까지 전파되는가?
```

내가 이해한 SOLID는 좋은 코드를 예쁘게 나누는 규칙이 아니었다.

변경이 번지는 방향을 통제하기 위한 원칙이었다.

---

# SRP: 하나의 actor에 대해서만 책임진다

SRP는 "클래스 하나에 기능 하나"라는 말보다, 하나의 actor에 대해서만 책임지라는 말에 가까웠다.

우리 회사의 `exsl` repo는 여러 플랫폼에서 함께 사용된다.

그 안에서 `RouteControl` 같은 클래스가 공통으로 사용되는데, 문제는 하나의 클래스가 여러 플랫폼의 요구사항을 동시에 책임진다는 점이다.

```text
AAOS 플랫폼 변경
다른 플랫폼 변경
고객사별 사양 변경
지도 연동 변경
HMI 표현 변경
경로 정책 변경
```

이 모든 변경 이유가 하나의 `RouteControl`로 들어오면, 그 클래스는 하나의 actor에 대해서만 책임지는 것이 아니다.

여러 actor의 변경 이유가 한곳에 모인 것이다.

처음에는 공통 코드라서 재사용성이 좋아 보일 수 있다.

하지만 플랫폼별 사양이 달라지기 시작하면 공통 코드는 안정적인 코드가 아니라, 가장 많은 변경 이유가 모이는 코드가 된다.

이때 해결이 반드시 상속이어야 하는 것은 아니다.

상속을 쓸 수도 있고, 정책 객체를 분리할 수도 있고, 플랫폼별 구현을 나눌 수도 있다.

중요한 것은 구현 기법이 아니라 변경 이유를 분리하는 것이다.

내가 이해한 SRP는 이렇게 정리된다.

> 같은 기능처럼 보여도, 다른 actor가 다른 이유로 변경을 요구한다면 같은 책임이 아니다.

---

# OCP: 새 사양은 확장으로 받아야 한다

OCP는 확장에는 열려 있고, 수정에는 닫혀 있어야 한다는 원칙이다.

내 경험에서는 `RouteOption` 구조가 떠올랐다.

SRP 때문에 JSON 설정을 따로 분리하는 과정에서, 상위에 `RouteOption`이 있고 하위에 `Option`, `EvOption`, `AvoidOption`이 있는 구조를 보게 됐다.

문제는 `RouteOption`이 하위 옵션들을 직접 생성하고 있었다는 점이다.

```text
RouteOption
├─ Option 직접 생성
├─ EvOption 직접 생성
└─ AvoidOption 직접 생성
```

처음에는 자연스러워 보인다.

`RouteOption`이 전체 옵션을 묶는 객체니까 하위 옵션을 만들 수 있다고 생각하기 쉽다.

하지만 `AvoidOption`에 플랫폼별 코드가 필요해지자 문제가 드러났다.

`AvoidOption`의 플랫폼별 구현이 바뀌었는데, 상위의 `RouteOption`도 수정해야 했다.

이건 OCP 관점에서 좋지 않다.

새로운 플랫폼 사양은 `AvoidOption` 구현체를 추가하는 방식으로 확장되어야 하는데, 기존 `RouteOption`까지 수정해야 했기 때문이다.

더 나은 구조라면 `RouteOption`은 구체 `AvoidOption`을 직접 만들지 않고 계약으로 받아야 한다.

```text
RouteOption
→ AvoidOption interface

Platform 조립부
→ DefaultAvoidOption
→ PlatformAvoidOption
```

내가 이해한 OCP는 이렇게 정리된다.

> 변경 가능성이 큰 하위 구현이 바뀔 때, 안정적이어야 할 상위 객체까지 수정된다면 OCP가 약한 것이다.

---

# LSP: 다르게 써야 한다면 같은 타입이 아니다

LSP는 처음에는 실무 사례가 잘 떠오르지 않았다.

나는 상속과 override를 많이 쓰지 않고, 사용하는 쪽에서 다르게 써야 하는 순간이 보이면 보통 분리하려고 했기 때문이다.

그런데 생각해보니 그 감각 자체가 LSP와 닿아 있었다.

RouteEngine에 `Cona`와 `Baidu` 두 엔진이 있다고 해보자.

둘을 같은 `RouteEngine`처럼 묶었지만 사용법이 다르다면 문제가 생긴다.

```text
ConaEngine은 이런 순서로 호출해야 한다.
BaiduEngine은 다른 순서로 호출해야 한다.
Cona와 Baidu의 옵션 변환이 다르다.
실패 처리도 다르다.
```

그 차이를 `RouteControl`이 알아야 한다면, `RouteControl`은 더 이상 `RouteEngine`이라는 부모 계약만 믿고 사용하는 것이 아니다.

자식이 무엇인지 알아야 한다.

```text
RouteControl
→ Cona인지 확인
→ Cona 방식으로 호출

RouteControl
→ Baidu인지 확인
→ Baidu 방식으로 호출
```

이 순간 치환 가능성은 깨진다.

부모 타입으로 받았는데 자식 타입을 알아야 안전하게 사용할 수 있기 때문이다.

내가 이해한 LSP는 이렇게 정리된다.

> 부모를 상속받았으면 부모의 계약도 물려받아야 한다.  
> 자식이 뭔지 알아야 쓸 수 있다면, 같은 타입으로 묶으면 안 된다.

---

# ISP: 사용하지 않는 계약은 변경 통로가 된다

ISP는 클라이언트가 자신이 사용하지 않는 메서드에 의존하지 않게 하라는 원칙이다.

내 경험에서는 `RouteExternal`이 떠올랐다.

`RouteExternal`에는 외부 연동으로 나가는 여러 interface가 한꺼번에 들어 있었다.

```text
SOME/IP 송출
NaviProvider 송출
CAN 송출
기타 외부 모듈 송출
```

모두 "외부로 보낸다"는 점에서는 비슷해 보인다.

하지만 변경 이유는 다르다.

```text
SOME/IP
→ service availability
→ protocol field
→ 통신 상태

NaviProvider
→ 안내 상태
→ provider contract
→ 화면/지도 연동

CAN
→ 100ms 송출 간격
→ signal packing
→ 차량 네트워크 제약
```

이 모든 것을 하나의 큰 `RouteExternal` 계약으로 묶으면, 특정 외부 연동의 제약이 전체 계약에 퍼진다.

예를 들어 CAN에 100ms 송출 간격이 필요해지면, CAN만의 제약이어야 할 것이 `RouteExternal` 전체의 관심사가 될 수 있다.

더 나은 구조라면 외부 연동별로 작은 interface를 나누고, `RouteExternal`은 필요한 interface들을 구현하거나 내부 구현체에 위임하면 된다.

```text
SomeIpRouteSender
NaviProviderRouteSender
CanRouteSender
```

구현체는 하나일 수 있다.

하지만 사용하는 쪽은 자신에게 필요한 계약만 알아야 한다.

내가 이해한 ISP는 이렇게 정리된다.

> 사용하지 않는 함수는 단순히 불필요한 함수가 아니다.  
> 나와 상관없는 변경 이유가 들어오는 통로다.

---

# DIP: 비즈니스 로직이 구현체 사용법에 맞춰지면 안 된다

DIP는 의존성 방향에 대한 원칙이다.

내 경험에서는 `RouteEngine`이 가장 잘 떠오른다.

`RouteControl`은 비즈니스 흐름에 가까운 역할을 한다.

그런데 `Cona`와 `Baidu` 엔진의 사용법이 다르고, 그 차이를 `RouteControl`이 직접 알고 있다면 의존성 방향이 잘못된 것이다.

이 사례는 LSP와도 연결되지만, DIP에서 보는 지점은 조금 다르다.

LSP는 `Cona`와 `Baidu`를 같은 타입으로 믿고 사용할 수 있는지를 묻는다.

DIP는 `RouteControl`이 왜 엔진의 구체 사용법을 알고 있어야 하는지를 묻는다.

```text
RouteControl
→ Cona 사용법을 안다
→ Baidu 사용법을 안다
→ 엔진별 호출 순서와 옵션 변환을 안다
```

이 구조에서는 비즈니스 로직이 엔진의 구체 사용법에 맞춰진다.

좋은 방향은 반대다.

`RouteControl`이 자신에게 필요한 계약을 정의하고, 각 엔진 adapter가 그 계약을 구현해야 한다.

```text
RouteControl
→ RouteSearcher interface

ConaRouteSearcher
→ RouteSearcher 구현

BaiduRouteSearcher
→ RouteSearcher 구현
```

이렇게 되면 `RouteControl`은 Cona와 Baidu의 차이를 모른다.

각 엔진의 호출 순서, 옵션 변환, 결과 변환은 adapter 안으로 들어간다.

내가 이해한 DIP는 이렇게 정리된다.

> 비즈니스 로직이 구현체 사용법에 맞추는 것이 아니라, 구현체가 비즈니스 로직의 계약에 맞춰야 한다.

# SOLID를 관통하는 질문

각 원칙은 서로 다른 질문을 던진다.

```text
SRP
→ 이 코드를 바꾸라고 요구하는 actor는 하나인가?

OCP
→ 새 사양이 들어왔을 때 기존 안정 코드를 수정하지 않고 확장할 수 있는가?

LSP
→ 같은 타입으로 묶인 구현체를 정말 같은 방식으로 믿고 사용할 수 있는가?

ISP
→ 사용하는 쪽이 필요 없는 계약까지 알고 있지는 않은가?

DIP
→ 의존성이 안정적인 정책을 향하고 있는가?
```

하지만 결국 내게는 하나의 질문으로 모인다.

> 이 변경은 어디까지 전파되어야 하는가?

SOLID는 원칙 이름을 외우기 위한 것이 아니었다.

변경 이유, 책임, 계약, 의존성 방향을 코드 안에 표현하기 위한 기준이었다.

좋은 구조는 사람이 조심해서 유지되는 구조가 아니다.

좋은 구조는 변경이 잘못된 곳으로 퍼지지 못하게 막는 구조다.
