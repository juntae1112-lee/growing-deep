# 왜 우리는 책임을 분리해야 할까

처음에는 클래스를 나누는 일이 단순히 코드를 보기 좋게 정리하는 작업처럼 느껴졌었다.

기능만 잘 동작하면 되는 것 아닌가 싶었고, 실제로 일정이 바쁜 프로젝트에서는 하나의 클래스 안에 여러 역할이 들어가는 경우도 많았다.

나 역시 비슷한 경험이 있었다.

하나의 Controller 안에서:

- 외부 시스템 호출
- 응답 데이터 가공
- 상태 관리
- 데이터 정렬 및 필터링
- UI 전달 데이터 생성

같은 작업들을 모두 처리하고 있었다.

처음에는 이 방식이 오히려 효율적으로 느껴졌다.

관련 로직이 한 곳에 모여 있었기 때문에 흐름을 따라가기 쉬워 보였고, 기능을 추가하는 속도도 빨랐다.

---

하지만 시간이 지나면서 Controller는 점점 무거워지기 시작했다.

하나의 변경을 위해 여러 흐름을 함께 확인해야 했고, 특정 데이터 하나를 수정하려 해도 외부 시스템 호출부터 상태 관리, UI 전달까지 모두 살펴봐야 했다.

즉:

> 하나의 클래스가 너무 많은 책임을 가지기 시작하면,
> 코드 이해와 유지보수 비용도 함께 증가한다.

---

문제는 단순히 코드가 길어지는 것이 아니었다.

더 큰 문제는 변경의 전파 범위였다.

예를 들어 데이터 정렬 방식을 수정하려고 해도:

- 응답 데이터 처리
- 상태 저장
- UI 전달 데이터 생성

까지 함께 영향을 받을 수 있었다.

즉:

> 책임이 섞인 코드는 작은 변경도 넓은 범위로 퍼지기 쉽다.

---

이미 프로젝트가 상당히 진행된 상태에서는 구조를 크게 바꾸기 어려웠다.

그래서 당시 내가 할 수 있었던 최선은 Controller 내부의 흐름을 함수 단위로 분리하는 것이었다.

예를 들면:

- 외부 시스템 호출 함수
- 응답 변환 함수
- 상태 갱신 함수
- UI 전달 데이터 생성 함수

처럼 역할별로 경계를 나누려고 했다.

물론 이것만으로 좋은 구조가 되는 것은 아니었다.

하지만 최소한 하나의 함수가 너무 많은 일을 하지 않도록 만들고, 변경이 필요한 위치를 조금이라도 좁히는 데에는 도움이 되었다.

---

이 경험 이후 클래스를 바라보는 관점이 조금 달라졌다.

클래스를 분리한다는 것은 단순히 코드를 예쁘게 정리하는 일이 아니었다.

오히려:

> 수정 이유가 다른 코드들을 분리하고,
> 변경의 전파 범위를 제한하는 일

에 가까웠다.

---

만약 같은 구조를 다시 설계할 수 있다면, 나는 하나의 Controller에 모든 책임을 몰아넣지 않을 것이다.

예를 들면:

```kotlin
class DataProvider
class DataMapper
class StateStore
class DataDispatcher
class Controller
```

처럼 책임을 나눌 것 같다.

각 클래스는 하나의 역할만 담당한다.

- DataProvider 는 외부 시스템과 통신한다.
- DataMapper 는 데이터를 변환한다.
- StateStore 는 상태를 관리한다.
- DataDispatcher 는 외부 전달을 담당한다.
- Controller 는 전체 흐름을 조율한다.

---

이렇게 분리하면 특정 기능이 변경되더라도 영향 범위가 훨씬 작아진다.

예를 들어 데이터 변환 규칙이 변경되면 DataMapper만 수정하면 된다.

상태 저장 방식이 변경되면 StateStore만 수정하면 된다.

즉:

> 변경의 이유와 수정 위치가 자연스럽게 연결된다.

---

실제로 이후 다른 프로젝트를 진행하면서는 최대한 하나의 클래스가 하나의 책임만 가지도록 설계하려고 했다.

그러다 보니 자연스럽게 얻은 장점들이 있었다.

- 재사용성이 좋아졌다.
- 테스트 범위가 작아졌다.
- 코드 이해가 쉬워졌다.
- 변경 전파가 줄어들었다.

무엇보다:

> "이 코드는 왜 수정해야 하는가?"

를 훨씬 명확하게 설명할 수 있게 되었다.

---

처음에는 책임 분리가 단순한 코드 정리 기술이라고 생각했었다.

하지만 이후에는 조금 생각이 달라졌다.

좋은 구조는 결국:

> 수정 이유가 다른 코드들을 분리하고,
> 변경의 전파 범위를 제한하기 위한 장치

에 더 가까운 문제였던 것 같다.
