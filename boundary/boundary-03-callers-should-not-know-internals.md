# 내부 문제를 호출자에게 넘기지 마라

> 내부 지연을 호출 순서로 맞추게 만들면, 호출자는 더 이상 API만 사용하는 것이 아니다.

오늘도 일하다가 답답한 상황을 만났다.

처음에는 단순한 호출 순서 문제처럼 보였다.

기존에 약속된 순서는 이랬다.

```text
1. 현재 위치로 지도 이동을 요청한다.
2. 그 다음 화면 전환을 요청한다.
```

탐색 쪽에서는 이 순서대로 호출하면 된다고 생각했다.

탐색은 경로와 위치를 계산한다.

그리고 지도에 필요한 요청을 보낸다.

지도는 그 요청을 받아 화면에 표현한다.

여기까지는 역할이 나뉘어 있었다.

그런데 화면 전환 과정에서 지연이 생겼다.

화면 전환이 늦어지고, 렌더링된 지도가 실제 UI에 제때 보이지 않는 문제가 발생했다.

그러자 요청이 바뀌었다.

```text
1. 먼저 화면 전환을 요청한다.
2. 그 다음 현재 위치로 지도 이동을 요청한다.
```

겉으로 보면 단순히 두 호출의 순서를 바꾸면 되는 문제처럼 보인다.

실제로 코드로 바꾸는 것도 가능하다.

하지만 내가 불편했던 지점은 "구현할 수 있는가"가 아니었다.

요청 순서가 반대로 바뀌는 순간, 문제의 성격도 바뀌었다.

이 순서를 내가 바꾸기 시작하면, 탐색이 지도 내부 사정을 알아야 한다는 점이 문제였다.

---

# 나는 왜 지도 내부 사정을 알아야 할까

탐색이 알아야 하는 것은 경로와 위치다.

탐색은 현재 위치로 이동해달라고 지도에 요청할 수 있다.

하지만 지도 내부에서 화면 전환이 얼마나 늦어지는지, 렌더링이 언제 UI에 반영되는지까지 알 필요는 없다.

그건 지도나 화면 전환을 처리하는 쪽의 내부 사정이다.

그런데 호출 순서를 바꿔달라는 요청은 탐색에게 이런 정보를 알라고 요구하는 것과 비슷하다.

```text
탐색
→ 지도 이동 요청
→ 화면 전환 지연 고려
→ 렌더링 반영 시점 고려
→ 호출 순서 변경
```

이렇게 되면 탐색은 더 이상 정해진 API만 호출하는 쪽이 아니다.

지도 내부의 지연과 화면 반영 타이밍을 맞춰주는 쪽이 된다.

내가 불편했던 이유는 바로 이 지점이었다.

> 내가 왜 지도 내부 사정을 알아야 하지?

---

# 호출 순서를 바꾼다는 것은 책임을 가져온다는 뜻이다

호출 순서를 바꾸는 일은 생각보다 크다.

단순히 코드 두 줄의 위치를 바꾸는 문제가 아니다.

순서를 바꾸려면 그 순서가 왜 필요한지 알아야 한다.

이번 경우에는 탐색이 원래 몰라도 됐던 정보를 알아야 했다.

```text
화면 전환은 언제 끝나는가?
지도 이동은 언제 호출해야 안전한가?
렌더링은 언제 UI에 반영되는가?
```

이 정도만 알아도 이미 탐색의 관심사를 넘어선다.

그 순간 탐색은 지도 API를 사용하는 쪽에서, 지도 내부 흐름을 맞춰주는 쪽으로 바뀐다.

원래는 이렇게 되어야 한다.

```text
탐색
→ 지도 API 계약
```

하지만 순서를 탐색이 보정하기 시작하면 이렇게 된다.

```text
탐색
→ 지도 내부 지연
→ 렌더링 반영 시점
→ 화면 전환 완료 시점
```

이건 좋은 경계가 아니다.

# 현상 설명이 곧 해결책은 아니다

논의가 답답했던 이유는 서로 보고 있는 지점이 달랐기 때문이다.

상대는 특정 메소드에서 시간이 줄어드는 현상을 설명하고 있었다.

이벤트 큐에 작업이 들어가고, 실제 처리가 늦어지면 시간은 줄어들 수 있다.

그 설명은 맞을 수 있다.

하지만 그 현상을 맞게 설명했다고 해서 해결책이 정해지는 것은 아니다.

중요한 질문은 따로 있다.

```text
그 지연을 호출자가 알아야 하는가?
그 지연을 호출자가 대신 맞춰야 하는가?
그 지연 때문에 기존 호출 순서를 뒤집어야 하는가?
```

내가 보고 있던 것은 메소드 하나의 처리 시간이 아니었다.

전체 흐름이었다.

```text
요청이 들어간다.
이벤트 큐에 쌓인다.
실제 처리가 늦어진다.
렌더링이 UI에 반영된다.
다음 호출이 실행된다.
```

비동기 문제는 메소드 하나만 보면 이해하기 어렵다.

큐에 언제 들어가는지, 실제 처리가 언제 되는지, 완료 시점을 어떻게 알 수 있는지까지 봐야 한다.

그리고 그 흐름을 누가 보장할 것인지 정해야 한다.

---

# API는 메소드 목록이 아니라 약속이다

API는 단순히 호출 가능한 메소드 목록이 아니다.

API는 호출자가 무엇을 믿어도 되는지에 대한 약속이다.

호출자는 이런 것을 알 수 있어야 한다.

```text
언제 호출할 수 있는가?
호출하면 무엇이 보장되는가?
언제 끝났다고 볼 수 있는가?
실패하면 어떤 상태가 되는가?
다음 호출은 무엇을 기준으로 할 수 있는가?
```

만약 화면 전환이 끝난 뒤에만 지도 이동이 안전하다면, 그 사실은 API로 드러나야 한다.

예를 들면 이런 방식이 있을 수 있다.

```text
화면 전환 완료 이벤트
지도 이동 가능 상태
화면 전환 후 지도 이동 API
화면 전환과 지도 이동을 함께 처리하는 API
```

방식은 여러 가지일 수 있다.

중요한 것은 호출자가 내부 지연을 추측하지 않게 만드는 것이다.

API를 제공하는 쪽이 안전한 호출 시점이나 통합된 동작을 약속해야 한다.

그 약속 없이 "이번에는 순서를 반대로 호출해달라"고 하면 호출자는 내부 구현을 추측해야 한다.

그리고 내부 구현이 바뀔 때마다 호출자도 함께 바뀌어야 한다.

---

# 리스크는 사라진 것이 아니라 호출자에게 퍼진다

이런 문제는 이번 호출 순서에만 한정되지 않는다.

비슷한 문제를 공용 상세정보 화면에서도 겪은 적이 있다.

여러 진입점이 같은 상세정보 화면을 열었다.

하지만 로딩 처리, 상세 데이터 요청, 실패 처리, 화면 전환을 각자 구현하고 있었다.

처음에는 각 모듈이 자기 흐름을 처리하는 것처럼 보였다.

하지만 실제로는 하나의 사용자 의도에서 발생하는 리스크를 여러 모듈에 나눠 가진 구조였다.

그 결과 한쪽에는 로딩이 있고, 다른 쪽에는 로딩이 없었다.

한쪽은 새 사양을 반영했고, 다른 쪽은 예전 흐름을 유지했다.

이번 호출 순서 문제도 비슷하다.

내부 지연과 순서 보장을 API 제공자가 감싸지 않으면, 그 리스크는 모든 호출자에게 퍼진다.

각 호출자는 자기 방식으로 순서를 맞춘다.

각 호출자는 자기 방식으로 지연을 고려한다.

각 호출자는 자기 방식으로 예외를 처리한다.

이것은 문제를 해결한 것이 아니다.

리스크를 모든 호출자에게 퍼뜨린 것이다.

```text
한곳에서 관리되는 리스크
→ 테스트할 수 있다
→ 설명할 수 있다
→ 수정 위치가 명확하다

여러 호출자에게 퍼진 리스크
→ 호출자마다 다르게 처리된다
→ 특정 진입점에서만 버그가 난다
→ 수정해야 할 위치가 늘어난다
```

좋은 경계는 리스크를 없애는 것이 아니다.

리스크가 관리될 위치를 정하는 것이다.

리스크가 한곳에 있으면 테스트하고, 설명하고, 수정할 수 있다.

하지만 리스크가 여러 호출자에게 퍼지면 어느 한 곳에서도 전체를 보장할 수 없다.

# 당장의 해결과 유지보수 가능한 해결은 다르다

이런 논의가 어려워지는 순간은 서로 다른 의견이 있을 때가 아니다.

문제가 "어떻게 해결할 것인가"에서 "누가 맞았는가"로 바뀔 때다.

특정 메소드에서 시간이 줄어든다는 설명은 맞을 수 있다.

그리고 호출자가 순서를 바꾸는 방식으로도 당장의 이슈는 닫힐 수 있다.

하지만 이슈를 닫는 방식이 모두 같은 것은 아니다.

어떤 방식은 지금 화면 하나를 고친다.

어떤 방식은 같은 문제가 다시 생기지 않도록 경계를 정리한다.

내가 신경 쓰는 지점은 "닫히는가"만이 아니었다.

이 방식으로 닫았을 때, 이후에도 유지보수 가능한가였다.

중요한 것은 다음 질문이다.

```text
현재 이슈가 어떤 순서에서 발생하는가?
어떤 내부 지연이 영향을 주는가?
호출자는 무엇을 믿고 호출할 수 있는가?
API 제공자는 무엇을 보장해야 하는가?
이번 대응이 다른 호출자에게도 반복되어야 하는가?
같은 문제가 다시 발생하지 않으려면 약속이 어떻게 바뀌어야 하는가?
```

설계 논의의 목적은 상대를 이기는 것이 아니다.

문제를 재현하고, 흐름을 합의하고, 책임 경계를 정하고, 같은 문제가 다시 생기지 않게 만드는 것이다.

그 과정에서 가장 쓸모없는 질문은 "누가 맞았는가"일 때가 많다.

더 중요한 질문은 이것이다.

> 이 이슈를 유지보수 가능한 방식으로 닫고 있는가?

# 직감은 기록으로 바꿔야 한다

이번 일을 겪으면서 다시 느꼈다.

나는 어떤 구조를 보면 꽤 빠르게 불편함을 느끼는 편이다.

"이렇게 하면 나중에 문제가 생길 것 같은데?"

"이 책임이 여기 있으면 안 될 것 같은데?"

"지금은 닫히겠지만 다음에 더 크게 터질 것 같은데?"

이런 감각이 먼저 온다.

하지만 직감만으로는 설득할 수 없다.

내가 아무리 위험하다고 느껴도, 상대가 볼 수 있는 형태로 바꾸지 못하면 그건 그냥 내 주장처럼 보인다.

그래서 앞으로는 불편함이 올라올 때 바로 말로 싸우기보다, 먼저 문서로 바꾸려고 한다.

최소한 이 정도는 적어야 한다.

```text
이상한 지점
→ 호출자가 지도 내부 지연을 고려해 호출 순서를 바꿔야 한다.

위험
→ 탐색이 지도 내부 구현에 의존한다.
→ 다른 호출자도 같은 보정 로직을 반복할 수 있다.
→ 지도 내부 구현이 바뀌면 호출자도 함께 바뀐다.

선택지
→ A. 호출자에서 순서 보정
→ B. API 제공자가 완료 이벤트나 통합 API 제공
```

이렇게 적으면 논의의 중심이 달라진다.

"누가 맞았는가"가 아니라 "어떤 리스크를 선택할 것인가"가 된다.

호출자에서 순서를 바꾸는 선택도 할 수 있다.

하지만 그 선택을 하려면 그것이 어떤 리스크를 만드는지 알고 해야 한다.

반대로 API 제공자가 완료 이벤트나 통합 API를 제공하는 선택도 할 수 있다.

이 경우에는 API 제공 쪽이 순서와 내부 지연을 감싸야 한다.

둘 중 무엇이든 선택할 수 있다.

다만 선택은 감으로 하는 것이 아니라, 리스크를 보고 해야 한다.

회의에서 같은 말이 계속 반복될 때도 있다.

그럴 때 계속 목소리를 높이면 결국 논의는 더 흐려진다.

그럴 때는 이렇게 말하는 편이 낫다.

```text
이건 말로 계속하면 같은 얘기가 반복될 것 같아서,
제가 시퀀스와 리스크를 문서로 정리하겠습니다.
```

이 말은 도망가는 말이 아니다.

오히려 논의를 말싸움에서 설계 판단으로 옮기는 말이다.

직감으로 위험을 감지하는 것에서 끝나면 감정이 된다.

직감을 리스크와 선택지로 바꿀 때 설계 논의가 된다.

그리고 나는 모든 위험을 몸으로 막을 필요는 없다.

위험을 설명하고, 기록하고, 선택할 수 있게 만드는 것도 책임이다.

# 내가 얻은 결론

이번 문제는 단순한 호출 순서 문제가 아니었다.

진짜 질문은 이것이었다.

> 내부 지연을 호출자가 대신 맞춰야 하는 구조가 되어도 되는가?

탐색은 지도 내부의 렌더링 지연을 알 필요가 없어야 한다.

탐색은 화면 전환의 내부 큐와 완료 시점을 추측하지 않아야 한다.

탐색은 정해진 약속을 믿고 API를 호출할 수 있어야 한다.

만약 그 약속대로 호출했는데 문제가 생긴다면, 호출자가 내부 순서를 맞춰주는 것이 아니라 API 약속이 바뀌어야 한다.

좋은 경계는 내부 사정을 호출자에게 설명하게 만들지 않는다.

호출자가 내부 사정을 몰라도 안전하게 사용할 수 있게 만든다.

결국 내가 느낀 불편함은 이것이었다.

> 내가 할 수 있는 일을 거절한 것이 아니라, 내가 알아서는 안 되는 일을 거절한 것이다.

경계는 "할 수 있는가"로 정해지지 않는다.

경계는 "알아야 하는가"로 정해진다.

할 수 있어도 알면 안 되는 것이 있다.

그것을 코드로 막는 것이 약속이고, 그 약속을 지키는 것이 아키텍처다.

그리고 그 약속이 흔들릴 때, 나는 먼저 이상한 지점과 리스크와 선택지를 기록해야 한다.

그게 내 직감을 설계 논의로 바꾸는 방법이다.
