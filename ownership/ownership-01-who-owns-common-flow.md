# 같은 사용자 의도는 하나의 Feature가 책임져야 한다

> 같은 화면을 여는 것이 중요한 게 아니라, 같은 사용자 의도를 하나의 흐름으로 책임지는 것이 중요하다.

하나의 공용 패널을 세 모듈이 함께 쓰고 있었다.

겉으로는 괜찮아 보였다.

같은 패널을 재사용하니 UI도 일관되고, 중복도 줄어든 것처럼 보였다.

하지만 시간이 지나면서 이상한 문제가 생겼다.

같은 패널인데 어떤 진입점에서는 로딩이 돌고, 어떤 진입점에서는 로딩이 돌지 않았다.

표현도 조금씩 달랐다.

사용자 입장에서는 같은 행동을 한 것 같은데 다른 경험이 나왔다.

처음에는 단순히 한쪽 구현이 빠진 문제처럼 보였다.

하지만 다시 보면 문제는 더 깊었다.

> 패널은 공용이었지만, 사용자 흐름은 공용이 아니었다.

각 모듈은 같은 패널을 사용하면서도 자신만의 방식으로 데이터를 전달하고, 로딩을 처리하고, 실패를 다루고, 화면을 열고 있었다.

공유한 것은 UI 조각이었고, 공유하지 못한 것은 사용자 경험이었다.

결국 이 구조에는 하나의 중요한 책임이 비어 있었다.

> 이 흐름을 끝까지 책임지는 feature가 없었다.

---

# 같은 화면을 여는 두 개의 흐름

더 분명하게 느낀 사례는 경유지와 목적지 상세정보 화면이었다.

사용자가 상세정보 화면에 들어가는 경로는 여러 개였다.

- 지도 위에서 경유지나 목적지 핀을 선택한다.
- 목록에서 경유지나 목적지를 선택한다.

출발한 UI는 다르다.

하지만 사용자 의도는 같다.

> 이 장소의 상세정보를 보고 싶다.

그렇다면 로딩을 어떻게 보여줄지, 상세 데이터를 언제 요청할지, 실패하면 어떻게 처리할지, 어떤 화면으로 전환할지는 같은 기준을 따라야 했다.

하지만 실제로는 지도 진입점과 목록 진입점이 각각 상세정보 화면을 열고 있었다.

그래서 한쪽에는 로딩이 있고, 한쪽에는 로딩이 없었다.

한쪽은 새 사양을 반영했고, 다른 쪽은 예전 흐름을 유지했다.

개별 모듈 입장에서는 각자 자기 일을 한 것처럼 보일 수 있다.

하지만 제품 입장에서는 하나의 사용자 의도가 두 개의 흐름으로 갈라진 상태였다.

이때 내가 느낀 핵심은 이것이었다.

> 같은 화면을 연다고 해서 같은 feature인 것은 아니다.
>
> 같은 사용자 의도를 하나의 흐름으로 책임질 때 feature가 된다.

# 문제는 중복 코드가 아니라 중복된 책임이었다

처음에는 이런 상황을 보면 공통 로직을 빼야 한다고 생각하기 쉽다.

물론 틀린 말은 아니다.

하지만 "중복 코드를 제거하자"로 접근하면 문제가 작아진다.

내가 실제로 겪은 문제는 코드가 두 번 작성된 것이 아니었다.

하나여야 하는 책임이 여러 모듈에 나뉘어 있었다.

```text
지도 진입점
→ 장소 선택
→ 로딩 처리
→ 상세 데이터 요청
→ 상세 화면 전환

목록 진입점
→ 장소 선택
→ 로딩 처리
→ 상세 데이터 요청
→ 상세 화면 전환
```

이렇게 되면 두 흐름은 계속 같아야 한다.

하지만 계속 같아야 하는 흐름을 두 곳에서 관리하는 순간, 언젠가는 어긋난다.

사양이 바뀌면 두 곳을 모두 고쳐야 하고, 누군가는 변경 사실을 놓친다.

어느 한쪽만 고쳐지면 나머지는 버그가 된다.

이건 구현 중복보다 더 위험하다.

> 중복 코드는 눈에 보이지만, 중복된 책임은 처음에는 잘 보이지 않는다.

# Controller가 아니라 Feature가 소유해야 한다

처음에는 이런 흐름을 Controller에 모아야 하나 생각할 수도 있다.

Controller가 이벤트를 받고 상태를 연결하는 역할을 할 수는 있다.

하지만 여기서 중요한 것은 단순한 이벤트 전달이 아니다.

사용자가 어떤 장소를 선택했을 때:

- 로딩을 보여줄지
- 상세 데이터를 요청할지
- 실패를 어떻게 보여줄지
- 화면 전환을 어떻게 할지
- 유입 경로에 따라 어떤 차이를 허용할지

이 모든 것이 하나의 사용자 경험을 만든다.

그래서 나는 이 책임이 Controller보다는 feature에 있어야 한다고 생각한다.

```text
지도 진입점 ─┐
             ├─> PlaceDetailFeature.open(placeId, source)
목록 진입점 ─┘

PlaceDetailFeature
├─ loading
├─ detail request
├─ failure handling
└─ detail screen
```

각 진입점은 "사용자가 이 장소를 선택했다"는 사실만 전달한다.

그 이후의 흐름은 `PlaceDetailFeature`가 책임진다.

이렇게 되면 상세정보 화면으로 들어가는 모든 진입점은 같은 기준을 통과하게 된다.

그리고 로딩 정책이나 실패 처리가 바뀌어도 수정 지점은 하나가 된다.

# Feature는 폴더가 아니라 책임의 단위다

여기서 말하는 feature는 단순히 디렉터리 이름이 아니다.

`feature/place-detail` 같은 폴더를 만들었다고 해서 자동으로 ownership이 생기지는 않는다.

중요한 것은 그 feature가 어떤 사용자 의도를 책임지는지다.

내가 생각하는 feature 단위 개발은 이런 질문에서 시작한다.

```text
이 사용자 의도는 누구의 책임인가?
이 흐름의 사양 변경은 어디에서 시작되어야 하는가?
다른 모듈은 어디까지 접근할 수 있는가?
다른 모듈이 이 흐름을 직접 재구현할 수 있는가?
```

좋은 feature 경계는 "여기 코드를 쓰세요"가 아니라 "이 흐름은 여기로만 들어오세요"에 가깝다.

다른 모듈이 내부 로딩 처리나 상세 요청 로직을 직접 만질 수 있으면, 같은 문제가 다시 생긴다.

그래서 ownership은 문서나 말로만 정하면 부족하다.

코드로 강제되어야 한다.

```text
허용되는 흐름
→ PlaceDetailFeature.open(...) 호출

허용되면 안 되는 우회
→ 상세 데이터 직접 요청
→ 로딩 직접 처리
→ 상세 화면 직접 전환
```

우회가 가능하면, feature는 아직 충분히 소유하고 있지 않은 것이다.

---

# 내가 지금 더 믿는 방향

결국 내가 지금 더 맞다고 느끼는 방향은 module 단위보다 feature 단위다.

모듈은 구현의 위치를 나누기 쉽다.

하지만 사용자 경험은 모듈 경계대로 움직이지 않는다.

사용자는 지도에서 들어왔는지, 목록에서 들어왔는지 별로 중요하게 생각하지 않는다.

사용자에게 중요한 것은 "장소를 선택했더니 상세정보가 자연스럽게 열린다"는 하나의 흐름이다.

그래서 같은 사용자 의도라면 feature가 책임져야 한다.

그리고 그 책임은 코드로 강제되어야 한다.

> 공용 UI를 공유하는 것이 아니라, 같은 사양의 사용자 경험을 하나의 feature가 소유하게 해야 한다.

사양이 다르면 분리한다.

사양이 같으면 feature로 묶는다.

그리고 그 feature가 시작부터 끝까지 책임진다.

합의된 책임은 코드의 경계가 되어야 한다.
