# Source of Truth는 하나여야 한다

> Source of Truth는 값이 하나만 있어야 한다는 뜻이 아니라, 각 값의 역할이 명확해야 한다는 뜻이다.

최근에 꽤 골치 아픈 버그를 하나 봤다.

처음에는 단순한 보정 로직 문제처럼 보였다.

서버가 계산한 남은 시간이 있고, 클라이언트가 계산한 남은 시간이 있었다.

요구사항은 대략 이런 형태였다.

```text
서버가 계산한 남은 시간과
클라이언트가 전달한 남은 시간의 차이가 일정 범위 이내라면
클라이언트의 시간을 사용한다.
```

처음 들으면 그럴듯해 보인다.

클라이언트는 실제 주행 중인 현재 상태를 더 가깝게 보고 있을 수 있다.

서버 계산값보다 클라이언트의 값이 사용자 경험에 더 자연스러울 수도 있다.

그래서 차이가 크지 않다면 클라이언트 시간을 존중하자는 요구는 이해할 수 있다.

문제는 이 요구를 어디에서 어떻게 반영했느냐였다.

---

# 클라이언트의 시간을 존중하는 것과 기준값을 바꾸는 것은 다르다

문제의 핵심은 클라이언트 시간을 사용했다는 사실 자체가 아니었다.

클라이언트 시간을 존중하고 싶었다면 그렇게 할 수 있다.

하지만 서버의 기준값을 바꾸면 안 됐다.

서버는 경로 전체와 각 구간의 시간을 계산하고 있었다.

그렇다면 서버가 계산한 시간은 경로 시간 모델의 기준값에 가까웠다.

반면 클라이언트가 전달한 시간은 현재 주행 상황에서 관측한 값 또는 표시 보정을 위한 후보값에 가까웠다.

이 둘은 역할이 달랐어야 한다.

```text
서버 계산 시간
→ 경로/구간 시간 계산의 기준값

클라이언트 전달 시간
→ 현재 상태에서의 관측값 또는 보정 후보

표시 시간
→ 사용자에게 보여줄 최종 정책 결과
```

하지만 실제 구현에서는 이 역할이 섞였다.

클라이언트가 전달한 시간을 맞추기 위해 서버가 각 구간의 시간을 조정했다.

그리고 조정된 시간은 다시 클라이언트로 내려갔다.

클라이언트는 그 값을 기준으로 다시 남은 시간을 계산했다.

그 감소된 시간이 다시 서버로 올라갔다.

서버는 다시 그 값을 맞추기 위해 구간 시간을 조정했다.

이렇게 악순환이 생겼다.

```text
클라이언트 남은 시간
→ 서버가 구간 시간 조정
→ 조정된 시간이 클라이언트로 내려감
→ 클라이언트가 다시 남은 시간 계산
→ 감소된 시간이 다시 서버로 올라감
→ 서버가 다시 구간 시간 조정
```

이 구조에서는 어느 값이 기준인지 알 수 없어진다.

서버 시간도 기준이 아니고, 클라이언트 시간도 기준이 아니다.

둘 다 서로의 값을 보고 다시 바뀐다.

---

# 문제는 값이 두 개 있다는 것이 아니었다

처음에는 "서버 시간과 클라이언트 시간이 둘 다 있어서 문제인가?"라고 생각할 수 있다.

하지만 값이 여러 개 있는 것 자체는 문제가 아니다.

실무에서는 하나의 개념에도 여러 값이 존재할 수 있다.

```text
서버 계산값
클라이언트 관측값
캐시값
표시값
로그용 값
디버깅용 값
```

문제는 값의 개수가 아니다.

문제는 각 값의 역할이 흐려지는 것이다.

```text
어느 값이 기준값인가?
어느 값이 관측값인가?
어느 값이 보정값인가?
어느 값이 표시값인가?
어느 값이 캐시인가?
```

이 질문에 답하지 못하면 시스템은 무엇을 믿어야 할지 모르게 된다.

그리고 시스템이 무엇을 믿어야 할지 모르면, 서로의 값을 보정하다가 오히려 더 큰 오류를 만든다.

이번 문제도 그랬다.

클라이언트 값은 참고하거나 표시 정책에 사용할 수 있었다.

하지만 그것이 서버의 구간별 시간 모델을 다시 바꾸는 기준이 되면서 Source of Truth가 흐려졌다.

관측값이 기준값을 바꾸고, 바뀐 기준값이 다시 관측값을 바꾸는 구조가 된 것이다.

---

# 더 나은 구조는 역할을 분리하는 것이다

내가 생각하는 더 나은 구조는 단순하다.

서버는 자신의 계산 결과를 기준값으로 유지한다.

클라이언트는 자신의 관측값을 별도로 유지한다.

그리고 사용자에게 무엇을 보여줄지는 표시 정책에서 결정한다.

```text
serverRemainingTime
→ 서버가 계산한 기준값

clientRemainingTime
→ 클라이언트가 계산하거나 관측한 값

displayRemainingTime
→ 사용자에게 보여줄 최종 값
```

코드로 표현하면 이런 형태에 가깝다.

```kotlin
data class RemainingTime(
    val serverTime: Duration,
    val clientTime: Duration?,
    val displayTime: Duration
)
```

여기서 중요한 것은 `displayTime`이 존재한다는 점이다.

클라이언트 시간을 사용자에게 보여주고 싶다면, 표시값을 클라이언트 시간으로 선택하면 된다.

하지만 그 선택 때문에 서버의 기준 시간이 바뀌어서는 안 된다.

```text
서버 기준값
→ 유지한다

클라이언트 관측값
→ 별도로 보관한다

표시 정책
→ 어떤 값을 보여줄지 결정한다
```

이렇게 하면 클라이언트 시간을 존중하면서도 서버의 Source of Truth는 유지할 수 있다.

---

# 보정값은 기준값이 아니다

이번 문제를 보면서 가장 크게 느낀 것은 이것이다.

> 보정값은 Source of Truth가 될 수 없다.

보정값은 기준값을 대체하기 위한 값이 아니다.

보정값은 특정 상황에서 기준값을 어떻게 사용할지 결정하는 데 도움을 주는 값이다.

클라이언트 시간이 더 사용자 경험에 적합할 수 있다.

하지만 그렇다고 해서 서버의 경로 시간 모델 자체가 클라이언트 시간에 맞춰 다시 쓰여야 하는 것은 아니다.

서버가 계산한 기준값과 클라이언트가 관측한 값을 분리하고, 마지막 표시 단계에서 어떤 값을 사용할지 결정했어야 한다.

이 차이를 놓치면 보정은 더 이상 보정이 아니다.

시스템의 기준을 다시 쓰는 일이 된다.

---

# Source of Truth는 역할의 문제다

Source of Truth라는 말을 처음 들으면 하나의 값만 있어야 한다는 뜻처럼 느껴질 수 있다.

하지만 실무에서 값은 여러 개 존재한다.

서버에도 있고, 클라이언트에도 있고, 캐시에도 있고, 화면에도 있다.

그래서 더 중요한 것은 값의 개수가 아니라 역할이다.

기준값은 기준값으로 남아야 한다.

관측값은 관측값으로 남아야 한다.

보정값은 보정값으로 남아야 한다.

표시값은 표시값으로 계산되어야 한다.

이 역할이 섞이면 시스템은 서로의 값을 다시 보정하기 시작한다.

그리고 그 순간 오류는 단순 계산 실수가 아니라 구조적인 문제가 된다.

# 직감은 설명 가능한 언어가 되어야 한다

이런 문제를 보면 처음에는 "뭔가 이상한데"라는 느낌이 먼저 올 때가 있다.

이번 문제도 그랬다.

클라이언트 시간을 존중한다는 요구 자체는 이해할 수 있었다.

하지만 그 값을 서버의 기준 시간에 다시 반영하는 구조를 보면서, 이건 위험하다는 느낌이 먼저 들었다.

처음에는 그 느낌을 명확히 설명하기 어렵다.

그냥 "이렇게 하면 안 될 것 같은데"에 가깝다.

하지만 실무에서는 직감만으로는 사람을 설득하기 어렵다.

동작은 하고 있고, 일정은 있고, 요구사항은 이미 들어와 있다.

그 상황에서 "왠지 위험합니다"라고 말하는 것만으로는 구조를 바꾸기 어렵다.

그래서 중요한 것은 그 불편함을 설명 가능한 언어로 바꾸는 일이다.

이번 문제에서 그 언어는 Source of Truth였다.

```text
서버 계산값
→ 기준값

클라이언트 전달값
→ 관측값 또는 보정 후보

화면 표시값
→ 표시 정책의 결과
```

이 역할이 섞이면서 관측값이 기준값을 바꾸고, 바뀐 기준값이 다시 관측값을 바꾸는 피드백 루프가 생겼다.

이렇게 설명할 수 있을 때 "이상하다"는 감각은 설계 논의가 된다.

좋은 직감은 설명되지 않은 구조적 문제를 먼저 감지하는 능력에 가깝다.

하지만 좋은 개발자는 그 직감을 감정으로 끝내지 않고, 왜 위험한지 설명할 수 있는 언어로 바꿔야 한다고 느꼈다.

---

# 내가 얻은 결론

이번 버그는 단순한 시간 계산 버그가 아니었다.

Source of Truth가 흐려진 설계 문제에 가까웠다.

클라이언트의 시간을 존중하고 싶었다면, 서버의 기준값을 바꾸면 안 됐다.

서버는 기준값을 유지하고, 클라이언트는 관측값을 제공하고, 표시 정책이 최종 값을 선택했어야 한다.

결국 Source of Truth는 값이 하나만 있어야 한다는 말이 아니다.

각 값의 역할이 하나여야 한다는 말이다.

```text
기준값은 무엇인가?
관측값은 무엇인가?
보정값은 무엇인가?
표시값은 무엇인가?
어떤 값이 다른 값을 바꿀 수 있는가?
```

이 질문에 답하지 못하면 시스템은 쉽게 흔들린다.

좋은 구조는 여러 값을 하나로 뭉개는 구조가 아니다.

여러 값이 존재하더라도, 각 값의 역할과 변경 권한을 명확히 구분하는 구조다.

> Source of Truth는 값을 하나만 두는 것이 아니라, 무엇을 믿을지 명확히 정하는 것이다.
