# 공통 정책은 누가 소유해야 할까

> 공통 로직을 한곳에 모은다는 것은 구현을 합치는 일이 아니라, 변경 권한과 책임을 한곳에 모으는 일이다.

비슷한 코드가 여러 모듈에 있을 때, 처음에는 단순히 중복처럼 보인다.

하지만 모든 중복이 같은 의미를 가지는 것은 아니다.

어떤 중복은 우연히 코드가 비슷한 것이고, 어떤 중복은 하나여야 하는 제품 사양이 여러 곳에 복제된 것이다.

문제가 되는 것은 후자다.

같은 사양을 따라야 하는 로직이 여러 모듈에 흩어져 있으면, 처음에는 아무 문제 없이 동작한다.

기준이 같고, 결과도 같기 때문이다.

하지만 새로운 사양이 들어오고 한 모듈만 먼저 바뀌는 순간, 나머지 모듈은 모두 버그가 된다.

이때 문제는 단순히 코드가 중복됐다는 사실이 아니다.

> 하나여야 하는 판단 기준을 여러 모듈이 각자 소유하고 있었다.

---

# 충전기 번개 아이콘 예시

예를 들어 충전기 번개 아이콘을 생각해볼 수 있다.

충전 레벨에 따라 번개 아이콘의 표현이 달라진다고 해보자.

처음에는 기준이 같았다.

```text
충전 레벨이 낮으면 아이콘 A
충전 레벨이 중간이면 아이콘 B
충전 레벨이 높으면 아이콘 C
```

각 모듈이 이 로직을 따로 가지고 있어도 처음에는 문제가 없어 보인다.

결과가 같기 때문이다.

하지만 이후 추가 사양이 들어온다.

예를 들어 특정 충전 상태에서는 다른 아이콘을 보여야 한다.

한 모듈만 이 사양을 반영하면 나머지 모듈은 모두 잘못된 표현을 하게 된다.

사용자 입장에서는 같은 충전 상태가 화면마다 다르게 보인다.

이때 문제는 "아이콘 선택 함수가 중복됐다"가 아니다.

더 본질적인 문제는:

> 하나여야 하는 제품 사양이 여러 모듈에 복제되어 있었다.

---

# 같은 코드와 같은 정책은 다르다

모든 비슷한 코드를 공통화해야 하는 것은 아니다.

두 모듈이 비슷한 코드를 가지고 있더라도, 앞으로 서로 다른 이유로 변경될 가능성이 있다면 분리되어 있는 편이 낫다.

예를 들어 한 화면은 접근성을 위해 큰 아이콘을 사용하고, 다른 화면은 제한된 공간 때문에 작은 아이콘을 사용한다고 해보자.

이 경우 표현 구현은 달라질 수 있다.

억지로 하나의 UI 컴포넌트로 합치면 오히려 서로의 변경을 방해한다.

반대로 충전 상태에 따라 어떤 의미의 아이콘을 선택해야 하는지는 화면의 취향이 아니다.

그것은 모든 화면이 함께 따라야 하는 제품 정책에 가깝다.

즉 공통화의 기준은:

```text
지금 코드가 같은가?
```

가 아니라,

```text
앞으로도 같은 사양에 의해 함께 변경되어야 하는가?
```

에 더 가깝다.

---

# 사양이 같으면 묶고, 다르면 분리한다

내가 지금은 이렇게 정리하고 있다.

```text
사양이 다르다
→ 분리한다

사양이 같다
→ 하나의 정책으로 묶는다
→ 그 정책의 소유자를 정한다
```

사양이 다른데 공용으로 묶으면, 공통이라는 이름 아래 서로 다른 요구사항이 숨겨진다.

그러면 한쪽을 고칠 때 다른 쪽이 깨진다.

반대로 사양이 같은데 각 모듈이 알아서 구현하면, 변경 시점마다 누군가는 놓친다.

결국 같은 상태가 화면마다 다르게 표현되고, 사용자는 일관되지 않은 제품을 보게 된다.

그래서 중요한 질문은 이것이다.

> 이 로직을 합칠 수 있는가?

보다:

> 이 사양을 누가 끝까지 책임지는가?

에 가깝다.

---

# 공통화해야 하는 것은 화면이 아니라 판단 기준이다

공통 정책이 필요하다고 해서 모든 UI 구현을 하나로 합쳐야 하는 것은 아니다.

각 화면은 여전히 자신의 레이아웃, 크기, 애니메이션, 접근성 처리를 책임질 수 있다.

공통으로 가져가야 하는 것은 화면 자체가 아니라:

> 같은 입력에 대해 어떤 의미의 결과를 선택할 것인가

라는 판단 기준이다.

예를 들면 다음과 같은 형태가 될 수 있다.

```kotlin
enum class ChargingIndicator {
    LOW,
    NORMAL,
    HIGH
}

fun indicatorFor(level: Int, isCharging: Boolean): ChargingIndicator {
    // 공통 충전 상태 정책
}
```

각 모듈은 이 결과를 받아 자신의 환경에 맞게 렌더링한다.

```kotlin
val indicator = ChargingIndicatorPolicy.indicatorFor(level, isCharging)
render(indicator)
```

이렇게 하면 화면의 표현 책임과 제품 규칙의 책임을 분리할 수 있다.

그리고 사양이 바뀌었을 때 수정해야 할 기준점도 하나가 된다.

---

# 협의만으로는 부족하다

공통 정책은 협의가 필요하다.

이 규칙이 정말 공통 제품 사양인지, 아니면 모듈별로 달라질 수 있는 표현 정책인지 먼저 합의해야 한다.

하지만 "사양이 바뀌면 다 같이 고치자"는 합의만으로는 부족하다.

시간이 지나면 누군가는 변경 사실을 모르고, 누군가는 영향 범위를 다르게 이해한다.

결국 복제된 규칙은 다시 어긋난다.

협의는 구조로 이어져야 한다.

- 공통 정책을 제공하는 하나의 API를 둔다.
- 모듈은 정책을 재구현하지 않고 그 결과를 사용한다.
- 경계값과 예외 상태를 테스트로 고정한다.
- 모듈별 예외가 필요하면 몰래 분기하지 않고 별도 사양으로 드러낸다.

좋은 구조는 "규칙을 지켜주세요"에서 끝나지 않는다.

지키지 않기 어려운 형태로 책임을 만든다.

---

# 사람을 설득하는 것도 기술이다

이런 문제는 코드만의 문제가 아니었다.

실제로 공통으로 가야 한다고 생각한 흐름을 두 모듈은 협의해서 하나로 합쳤다.

하지만 한 모듈은 끝까지 자신들의 방식으로 남으려 했다.

그 과정에서 느낀 것은, 코드를 합치는 것보다 사람을 설득하는 일이 더 어렵다는 점이었다.

그리고 어쩌면 그 설득까지 포함해서 기술이라는 생각도 들었다.

아키텍처는 코드만으로 존재하지 않는다.

누가 책임질지, 누가 변경 권한을 가질지, 누가 버그를 끝까지 볼지에 대한 합의가 있어야 구조가 동작한다.

하지만 합의만으로는 오래가지 않는다.

합의된 책임은 코드의 경계가 되어야 한다.

결국 ownership은 코드와 사람 사이에 놓인 경계다.
